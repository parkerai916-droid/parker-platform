# Knowledge Discoverability and Governed Retrieval into Reasoning Context — Contract Design Bounded Semantic Relevance Amendment

Programme: **Reasoning Context Contract Design, Bounded Semantic Relevance Amendment (adopted).**

## 1. Purpose

This amendment establishes the minimum contractual concepts required to express Bounded Relevance Computation at the Reasoning Context Contract Design's own tier — request/input shape, candidate-result shape, canonical-identity handling, determinism, permission behaviour, and failure behaviour — without prematurely fixing any concrete Kotlin type, method signature, storage technology, or library, and without defining a second semantic mechanism. Every concept below either restates a concept `PROGRAMME_3_KNOWLEDGE_MEMORY_CONTRACT_DESIGN_V2_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` already fixed for Knowledge Retrieval, unchanged, or narrows it for the one respect in which this surface genuinely differs: `ReasoningKnowledgeSource` lawfully operates over dereferenced Memory Core content, where `KnowledgeRetrieval` does not.

## 2. Relevance Request Concept

A **Reasoning Context Relevance Request** is the contractual concept covering what may cross into the shared Unit 9.7 relevance mechanism from `DefaultReasoningKnowledgeSource`: the authorised query's relevance text, and a closed, Parker-supplied set of already-eligible candidates, each represented only by an opaque per-request identifier and the minimum content Section 3 (below) fixes. It is not a new public contract type with fixed fields; it is a contractual constraint on what any eventual type may contain — nothing more, and specifically not the candidate's permanent `KnowledgeId`, `MemoryCoreRecordReference`, evidential state, `KnowledgeItemStatus`, `StalenessDisclosure`, or the requesting principal's identity.

## 3. Opaque Per-Request Candidate Identity and Minimum Relevance Content

**Opaque identity.** Every candidate crossing into the shared mechanism is represented solely by an opaque, request-scoped, unlinkable token — never a `KnowledgeId`, a `MemoryCoreRecordReference`, or any other permanent identifier — mirroring `PROGRAMME_3_KNOWLEDGE_MEMORY_CONTRACT_DESIGN_V2_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 2 exactly.

**Minimum content, determined from the existing adopted contract, not assumed.** `DefaultReasoningKnowledgeSource`'s own existing, frozen algorithm (Reasoning Context Scope Lock Section 5, steps 7–9) already dereferences each item-level-approved candidate's `MemoryCoreRecordReference` into exactly one normalized `String` — for `ToAssertion`, the assertion's own `statement` text; for `ToEntity`, `listOf(entity.primaryLabel).plus(entity.aliases).joinToString(" | ")` — and matches `KnowledgeRetrievalQuery.relevance` against that single string before this amendment's own fallback could ever run. The minimum necessary content crossing into the shared relevance mechanism is **exactly that same single, already-computed, already-normalized content `String`, per candidate, and nothing more**: not the underlying `MemoryCoreRecordReference`, not the reference kind, not `evidentialState`, `status`, or `StalenessDisclosure`, and not any additional Memory Core field the existing algorithm does not already resolve for structural matching. This amendment does not assume `basis` text is sufficient here, and does not require it — the dereferenced `content` string the existing algorithm already produces is a strictly different, wider field than Unit 9's `basis`, and is the correct, already-adopted, already-minimal boundary for this surface specifically, not a new widening. No additional dereference, and no additional Memory Core call, is authorised merely to supply the relevance mechanism with more content than structural matching already required.

## 4. Relevance Result Concept

A **Reasoning Context Relevance Result** is the contractual concept covering what the shared mechanism may return to `DefaultReasoningKnowledgeSource`: an ordering or subset of the exact per-request identifiers it was given, and nothing else — never new identifiers, never free-text content, never any assertion about permission, lifecycle, evidential state, or eligibility. A Relevance Result is not itself a `SafeKnowledgeResultEntry`; it is a strictly narrower, intermediate concept that `DefaultReasoningKnowledgeSource` alone converts into one, exactly as Section 5 (below) requires — mirroring `PROGRAMME_3_KNOWLEDGE_MEMORY_CONTRACT_DESIGN_V2_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 3.

## 5. Canonical/Authoritative Re-Resolution

Every identifier a Reasoning Context Relevance Result contains must resolve, by `DefaultReasoningKnowledgeSource`'s own direct lookup against the exact candidate set it supplied, back to the exact canonical `KnowledgeItem` it originally represented — never to a competing or mechanism-supplied representation, and never to a candidate outside the exact set originally supplied for the current request. That resolution is completed, and the content ultimately disclosed is established, only through the fresh, second, already-governed Memory Core dereference Section 9 (below) fixes — never through the mechanism's own output, and never through a new or widened Memory Core operation. An identifier that fails to resolve against the originally supplied set is an integrity fault, rejected and never silently substituted; a token that resolves but whose fresh re-dereference (Section 9) no longer succeeds is excluded, not substituted, exactly as Section 9 fixes. The shared mechanism's own output is never itself authoritative content — it is only ever a lens onto candidates `DefaultReasoningKnowledgeSource` already, separately holds, exactly as the analogous Knowledge Retrieval-tier guarantee (`PROGRAMME_3_KNOWLEDGE_MEMORY_CONTRACT_DESIGN_V2_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 4) already establishes.

## 6. Distinction Between Relevance and Authority

A relevance ordering or score is not evidential-state classification, is not a truth determination, is not a permission decision, and is not itself an act of canonical authority. `KnowledgeItem.evidentialState`, `KnowledgeItem.status`, and `StalenessDisclosure` remain exclusively assigned and disclosed exactly as `DefaultReasoningKnowledgeSource` already computes them today, entirely unaffected by, and never influenced by, any relevance computation this amendment would authorise. A candidate surfaced by the shared mechanism is exactly as authoritative, and no more authoritative, than the exact same candidate would be if it had instead been found by the existing substring match — the relevance mechanism changes only *which* eligible, already-dereferenced candidates are surfaced when structural matching finds none, never *what standing* a surfaced candidate has once found, mirroring `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 8.

## 7. Structural-First, Exact-Zero-Only Fallback

Bounded Relevance Computation may run inside `DefaultReasoningKnowledgeSource` only as a fallback, strictly after the Reasoning Context Scope Lock's own frozen, ten-step locked algorithm (its Section 5) has completed every required Pre-computation stage through structural matching — lifecycle shaping, item-level authorization, governed dereference, and the existing substring match itself, its steps 4 through 9 — and that structural match has completed successfully with exactly zero relevant candidates from the full structurally-eligible, item-level-approved, dereferenced candidate set. This is not a claim that the entire ten-step algorithm, including its own final bounding step, has run; bounding (step 10) is never reached on the path this amendment governs until after Bounded Relevance Computation itself has run and Pre-disclosure (Section 9, below) has completed. This amendment incorporates, by reference and unweakened, the adopted Proposal's own bright-line rules (`PROGRAMME_3_UNIT_9_SEMANTIC_RELEVANCE_SCOPE_LOCK_REVISION_PROPOSAL.md` Section 16): fewer-than-`maximumResults` is not zero; one structural match prevents fallback; permission denial, lifecycle exclusion, dereference failure, and structural failure are none of them a fallback trigger. This amendment does not authorise running the shared mechanism concurrently with structural matching, or blending their outputs, and does not authorise fallback on any query where structural matching succeeds or fails.

## 8. Permission Ordering

Permission behaviour is entirely unchanged by this amendment. `PermissionEngine` remains the sole authority over every permission decision; the Reasoning Context Scope Lock's own frozen ten-step order (its Section 5) and the underlying Permission Enforcement Mechanism Clarification's evaluation order are untouched, unreordered, and un-shortened. A Reasoning Context Relevance Request may only be constructed from candidates that have completed Pre-computation — successfully passed act-level and item-level permission gates, lifecycle shaping, and governed dereference, sufficient for admission to the closed candidate set — and every Reasoning Context Relevance Result must still undergo Pre-disclosure, exactly as Section 9 (below) fixes it, never relying solely on the Pre-computation snapshot. Nothing in this amendment creates, implies, or permits an alternate or parallel permission pathway, and nothing in Section 9's own fresh checks is a new Memory Core or `PermissionEngine` capability — each is a second invocation of an operation Pre-computation already performed once.

## 9. Pre-Computation vs Pre-Disclosure

These remain the two distinct, non-substitutable checkpoints the adopted Unit 9.7 package already establishes for the Knowledge Retrieval surface (`PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Sections 3 and 5), extended and made concrete for this surface's own dereferenced-content boundary. **Pre-computation** is every existing required permission/lifecycle/dereference step the Reasoning Context Scope Lock's own Section 5 already fixes, before a candidate can enter the closed semantic candidate set.

**Pre-disclosure**, performed only for each candidate the shared mechanism actually surfaces — never the full candidate pool — comprises exactly three existing, already-governed operations, each already invoked once during Pre-computation and invoked a second time here; none is a new Memory Core, `KnowledgeItemPersistence`, or `PermissionEngine` capability:

1. **`KnowledgeItem` currentness.** A fresh `KnowledgeItemPersistence.find(knowledgeId)` lookup — the existing, already-governed single-item accessor the persistence interface already exposes — confirming the item still exists and remains eligible under `KnowledgeItem.status`.
2. **Permission currentness.** A fresh `PermissionEngine.evaluate` call for the same item-level intent Pre-computation already constructed, confirming current authorisation.
3. **Memory Core currentness and content.** A fresh, second invocation of the identical purpose-bound `MemoryRetrieval.getAssertion`/`getEntity` call the existing dereference step already makes once. Because that call returns the whole referenced record rather than a status-only projection, this single second call simultaneously establishes whether the record still exists, whether its `MemoryCoreRecordStatus` is still `ACTIVE` (a non-`ACTIVE` or absent result excludes the candidate — `DISPUTED`, `SUPERSEDED`, `ARCHIVED`, `DELETED`, and "no such record" all collapse into the identical "excluded" outcome the existing algorithm's own Pre-computation dereference already produces), and, only if still `ACTIVE`, its current content.

Any of the three checks failing excludes the candidate outright — never disclosed, never substituted. Where a candidate survives all three, the content used to construct `SafeKnowledgeResultEntry` is the freshly re-read content from check 3, never the Pre-computation-time snapshot the shared mechanism itself saw. This amendment does not claim an ability to detect that content changed between Pre-computation and Pre-disclosure as its own distinguishable signal — it claims only that whatever is disclosed is always current as of Pre-disclosure, because check 3 cannot be performed without receiving the record's then-current content. Neither Pre-computation nor Pre-disclosure is an alternative to the other; both are mandatory for every disclosed result.

## 10. Failure Semantics

Failure behaviour follows the Reasoning Context Contract Design's own existing discipline (its Section 9): distinguishable outcome categories, never silently conflated, and genuine implementation faults propagate honestly rather than being absorbed into a successful-looking result. Every relevance-specific failure case — mechanism unavailable, timeout, malformed output, an unknown, unauthorised, altered, duplicate, or stale/cross-request identifier, a permission or lifecycle change mid-computation, or an attempt to exceed the closed candidate set, mutate canonical persistence, or dereference beyond Section 3's own minimum-content boundary — is a sub-case of the Reasoning Context Contract Design's own existing failure discipline, never a new, independently-invented outcome category, and never triggers a second execution of the Scope Lock's own structural algorithm. The complete, binding table is fixed at `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 6 and restated, adapted only for this surface, in `REASONING_KNOWLEDGE_SOURCE_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 13; this amendment incorporates both by reference.

## 11. Deterministic Mechanism Identity/Version/Configuration

Identical query, identical canonical state, and identical frozen mechanism identity/version/configuration must together produce an identical result, including identical ordering, every time; a mechanism upgrade, replacement, or reconfiguration is itself a disclosed, governed change, never silent behavioural drift — the identical guarantee `PROGRAMME_3_KNOWLEDGE_MEMORY_CONTRACT_DESIGN_V2_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 6 already fixes for Knowledge Retrieval, incorporated here by reference and extended, unweakened, to this surface. Because Section 13 (below) requires the identical mechanism identity/version/configuration to be shared between both surfaces, a single mechanism upgrade is a single governed change reviewed once, not two independent ones.

## 12. Shared-Mechanism Dependency on the Implementation-Neutral Unit 9.7 Relevance Contract

This amendment does not define a semantic mechanism. It requires that any future implementation of `DefaultReasoningKnowledgeSource`'s own Bounded Relevance Computation depend on exactly the same implementation-neutral relevance mechanism contract `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 4 already fixes, and reuse the identical concrete mechanism Unit 9.7.1's contract types and Unit 9.7.3's own semantic-fitness-gated selection ultimately produce — not a second, independently selected, independently configured, or independently versioned mechanism. A single shared mechanism instance (or an equivalent, identically-configured instance) is authorised to serve both `DefaultKnowledgeRetrieval` and `DefaultReasoningKnowledgeSource`; nothing in this amendment requires or authorises two mechanism instances to diverge in behaviour, version, or configuration.

## 13. Prohibition on a Second Semantic Implementation

No sentence in this amendment may be read as authorising: a second embedding engine; a second QMD adapter or any other named implementation; a second ranking algorithm; a second semantic configuration authority; or any orchestration-level duplication of Unit 9.7's own fallback-trigger, closed-candidate-set, or integrity-validation logic beyond the minimum restatement `REASONING_KNOWLEDGE_SOURCE_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` performs for this surface's own, structurally distinct dereferenced-content boundary (Section 3, above). Where Unit 9.7's own contract and this amendment could be read to authorise two independently-behaving mechanisms, that reading is a misreading of this amendment; Section 12 (above) controls.

## 14. Implementation-Neutrality

Every concept in this amendment is stated without naming a specific library, embedding model, or storage technology. QMD and any embedding model appear only as the adopted Unit 9.7 package's own evidence, never as a named, required, or implied dependency of this amendment. A future implementation remains free to select any mechanism satisfying `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 4 and this amendment's Sections 2–11.

## 15. Compatibility with Existing `ReasoningKnowledgeSource` and `SafeKnowledgeResultEntry` Contracts

This amendment is additive only. It does not alter the Reasoning Context Contract Design's own layering, its eleven RESOLVED Decision-Register items, its Contract Invariants (its Section 13), or any other section beyond the single insertion below. It does not alter the frozen `ReasoningKnowledgeSource.recall` signature, the frozen `SafeKnowledgeResultEntry` field order, or any locked rendering/escaping rule (Reasoning Context Scope Lock Sections 4, 6). It is fully compatible with, and does not touch, the adopted Unit 9.7 package's own §8 determinism guarantee and error model, both extended by reference, never altered.
