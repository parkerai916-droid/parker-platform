## 2. The Question, Restated Precisely

When `ExecutionRequest.targetResources` is deliberately, permanently empty (Errata 004 §7's own already-frozen design for Memory Core's read and write decorators), how may `DefaultPermissionPolicy.evaluate` lawfully derive the `(PermissionAction, ResourceType)` pair Errata 004 §7's own frozen table already assigns to each Memory Core operation, given that `ActionMapper.mapOne`'s existing matching (`entry.mappings.filter { it.resourceType in targetResourceTypes }`) can never succeed against an empty `targetResourceTypes` set?

## 4. The Governance Tension Found, and How It Resolves

`docs/architecture/action-mapping.md`'s own "Validation" section (read in full for the first time in this document's own audit — neither prior Clarification read it) states: "A vocabulary entry's `applicableResourceTypes` **MUST** be checked against the actual `ResourceType`(s) of `ExecutionRequest.targetResources` at validation time. A mapped action whose declared resource types don't match any target Resource is also a validation failure." Read at face value and generally, this would also treat a genuinely **empty** `targetResources` as a validation failure for any vocabulary entry with a declared `applicableResourceTypes` — since "doesn't match any target Resource" is vacuously true when there are zero target Resources. Naively deriving `(action, resourceType)` from the Action Vocabulary alone, with no actual target Resource to check against, would appear to contradict this general rule.

**This is not a genuine contradiction between two governing documents; it is the ordinary, already-established relationship between a general rule and an already-accepted, more specific, later exception.** `action-mapping.md` describes the *default* case: an ordinary Planner-constructed request, where every protected object a request acts upon is assumed representable as a Resource Registry entry the Planner names in `targetResources`. Errata 004 §7 is later, more specific, already-accepted governance that explicitly, deliberately carves Memory Core's own two decorators out of that default — disclosing the tension itself ("Consequence this errata discloses rather than hides") and directing that the fix be "a policy/engine composition decision... made once, at `ParkerRuntime` construction," not a change to `action-mapping.md`, `ActionMapper`, or `ExecutionRequest`. This is the same "more specific, already-accepted governance controls over a more general default" reasoning the Contract Design's own Section 6 already relied on for Chapter 8 — extended here to `action-mapping.md`'s Validation section, on the identical logic, not a new principle invented for this document.

**This resolution is only sound if the resulting mechanism remains as narrow as Errata 004 §7 itself is** — confined to the closed, already-named set of actions Errata 004 §7 enumerates, never a general "any request with empty `targetResources` may skip Resource-based validation" rule. A general rule of that shape would relax `action-mapping.md`'s own Validation discipline for every future caller that happens to omit `targetResources`, for any reason, reviewed or not — a materially larger and un-authorised relaxation. The audit in Section 3 above confirms the closed set is genuinely closed today for literal, always-empty construction: exactly two decorator classes, nine action names total (`memory.create_provenance`, `memory.create_entity`, `memory.create_assertion`, `memory.create_relationship`, `memory.register_document`, `memory.transition_status`, `memory.delete_record`, `memory.retrieve`, `memory.retrieve_document`), all already named in Errata 004 §7's own frozen table.

## 5. The Critical Constitutional Question — Resource Existence vs. Resource Classification

**Resource existence** is the question Chapter 8's own invariant governs: is *this specific, individual protected object* represented in the Resource Registry, and therefore potentially accessible at all? For Memory Core, this question is answered — permanently, by already-accepted design (Errata 004 §7: "Memory Core records are never Resource Registry entries... there is never a Resource Registry entry to name, at any point in a Memory Core record's lifecycle") — **not** through Resource Registry membership, but through Memory Core's own, independently governed existence mechanism: a record either is or is not present in `InMemoryMemoryCore`/`DurableMemoryCore`'s own storage, established by `delegate.getEntity`/`getDocument`/etc. actually being called and returning non-null (Errata 004 §9: "Retrieve unconditionally from the delegate, then evaluate permission against the actual retrieved record's own kind"). This mechanism is unaffected by, and independent of, anything considered in this document.

**Resource classification for permission evaluation** is a coarser, different question: what *category* of protected object does this *class of action*, as a whole, act upon? This is precisely what an `ActionResourceMapping` already, lawfully answers for every other action in the system, and what Errata 004 §7's own frozen table already answers for Memory Core's nine action names — a classification of the **act**, never of any specific **object**.

**Can the Action Vocabulary (or an equivalent governed source) lawfully supply a `ResourceType` for permission evaluation here, without fabricating a Resource Registry entry or claiming a specific record is registered? Yes — provided the mechanism is confined to producing only a classification, never an existence claim.** This is verified, not merely asserted, by tracing what the mechanism does and does not touch:

1. **`ResourceRegistry` is never called.** `resourceRegistry.register`, `.update`, and `.resolve` are not invoked anywhere in this mechanism — Chapter 8's own "authoritative catalogue" gains no new entry, boundary-level or per-record, confirmed nowhere else in the runtime does either. (Errata 004 §7's own text forecloses even a fixed, boundary-level Resource Registry entry for Memory Core retrieval — unlike Knowledge Retrieval's `KNOWLEDGE_RETRIEVAL_RESOURCE_ID` — by its own repeated, explicit "`targetResources` is always `emptyList()`... there is never a Resource Registry entry to name" language; this document does not propose or reconsider that.)
2. **`PermissionDecision.resourceId` never claims a real resource.** `DefaultPermissionPolicy.evaluate`'s own existing fallback, `request.targetResources.firstOrNull() ?: ResourceId("no-target-resource")`, already produces the honest placeholder value for an empty `targetResources` list, unchanged by this mechanism — the produced decision never asserts a specific `ResourceId` exists or is registered.
3. **Existence and classification are established by structurally independent code paths.** Existence is Memory Core's own delegate lookup (Errata 004 §9), already complete before `isApproved` is ever called on the direct-lookup paths. Classification is a static, verb-phrase-keyed lookup against Errata 004 §7's own frozen table. Neither reads the other; the classification step cannot, even in principle, "prove" or imply that any specific record exists, because it never inspects any record at all — it inspects only the verb phrase, a property of the *act*, fixed before any specific record enters the picture.
4. **The resulting `PermissionDecision` answers only "may this Principal perform an act of this class at all," never "does this specific resource exist" or "is this specific resource registered."** This is the same act-level question `DefaultKnowledgeRetrieval`'s own act-level gate already, lawfully asks against its own fixed, registered boundary resource — the only difference is that Memory Core's own boundary is never registered anywhere, by Errata 004 §7's own already-accepted choice, so the classification is read from the frozen table directly rather than from a `Resource.resourceType` field.

**If this separation could not be maintained** — for example, if the mechanism populated `PermissionDecision.resourceId` with a fabricated value, or if `ResourceRegistry` gained an implicit entry as a side effect, or if the classification step ever consulted a specific record's own identity — **the mechanism would not be authorised**, and the narrower missing constitutional concept would need to be a genuinely new "protected object class" concept, distinct from both the individual-Resource model Chapter 8 already governs and the plain classification-only model this document selects. No governing document currently defines such a concept, and this document does not need to invent one, because the classification-only mechanism above satisfies the question without it.

## 6. Selected Resolution-Derivation Model

### A. Mechanism Authorised

**`DefaultPermissionPolicy`'s own resolution step may derive the `(PermissionAction, ResourceType)` pair for a proposed action directly from an explicit, closed, per-verb-phrase composition-time configuration — never from a general "empty `targetResources`" fallback — when, and only when, both of the following hold for a given `ExecutionRequest`:**

1. **`request.targetResources` is structurally empty** (not merely resolved-to-empty because a supplied `ResourceId` failed to resolve — the distinction `action-mapping.md`'s own Validation section's illustrative mismatch example does not itself need to draw, but which this mechanism must draw to avoid silently reinterpreting a genuine resolution failure as a deliberate design choice); **and**
2. **the specific proposed-action verb phrase is one of the closed, already-named set Errata 004 §7's own frozen table enumerates** (Section 4, above) — never any other verb phrase, regardless of whether its own `targetResources` happens to be empty.

**What is derived:** the `(PermissionAction, ResourceType)` pair Errata 004 §7's own frozen table already, specifically assigns to that verb phrase — **for the seven of the nine action names that are genuinely single-typed by their own name alone.** This includes, centrally, both action names this task's own audit trace actually concerns: `memory.retrieve` (`READ`/`MEMORY`) and `memory.retrieve_document` (`READ`/`DOCUMENT`), each unambiguous.

**Disclosed exception, not silently generalised over: `memory.transition_status` and `memory.delete_record` are not single-typed.** Errata 004 §7's own frozen table states their own resourceType is "`MEMORY`/`DOCUMENT` (per the transitioned record's own kind)" — information the verb phrase alone does not carry, and which `PermissionGatedMemoryCore.transitionStatus` (independently re-read: its own action-name selection distinguishes only delete-vs-not, never record kind, and passes no record-kind parameter into the `ExecutionRequest` it builds) does not supply either. A verb-phrase-keyed lookup, as this mechanism otherwise describes, cannot resolve a single pair for either of these two action names. Applying the same mechanism to them would require deriving a two-pair *set* (mirroring `ActionMapper`'s own already-supported composite-action shape: `{(WRITE, MEMORY), (WRITE, DOCUMENT)}` or `{(DELETE, MEMORY), (DELETE, DOCUMENT)}`) and relying on `DefaultPermissionPolicy`'s own existing "most restrictive wins" tie-break to select an outcome — safe against over-approval (a `DENIED` on either candidate wins), but capable of under-approving a transition that should be permitted for its own actual kind, because the *other* kind's own rule happens to be stricter. This document does not select that treatment, or any other, for these two action names — `PermissionGatedMemoryCore` is dormant and unused in the live composed runtime today (confirmed: no construction of it appears in `ParkerRuntime.kt`), and both action names fall outside this task's own named audit trace (the **read**-side path, `PermissionFilteredMemoryRetrieval → ExecutionRequest → DefaultPermissionPolicy.evaluate → ActionMapper → ActionMappingResult.Resolved`). Resolving them is deferred to a future, separate pass, if and when `PermissionGatedMemoryCore` is ever wired into live composition.

**From what governed source:** Errata 004 §7's own already-frozen mapping table, expressed as an explicit, disclosed configuration at `DefaultPermissionPolicy`'s own composition — the same location, and the same tier of decision ("a policy/engine composition decision, made once, at `ParkerRuntime` construction"), Errata 004 §7 itself already names. This is deliberately **not** expressed as a change to `ActionVocabulary`/`InMemoryActionVocabulary`'s own general contract, which every other, ordinarily-resourced caller in the system also relies on unchanged — `ActionVocabulary`'s own authority over the verb-phrase-to-`(action,resourceType)` mapping *content* is preserved (the values used are identical to what an `ActionVocabularyEntry` would already say), only the *mechanical registration surface* differs, exactly as Errata 004 §7 itself already anticipated. Whether these nine action names are *also*, redundantly, registered in `ActionVocabulary` for documentation/consistency is a harmless implementation detail this document does not decide.

**Under what conditions:** only the two conjunctive conditions above — never a general rule, never triggered by caller identity.

**What remains fail-closed:** everything, in two respects. First, every other action in the system — any caller whose `targetResources` is empty for a reason other than deliberate, already-governed design — continues to fail exactly as `action-mapping.md`'s own Validation section and `ActionMapper.mapOne`'s own existing `RESOURCE_TYPE_MISMATCH` path already require, completely unchanged. Second, and centrally: **this mechanism decision, by itself, adds no `PermissionPolicyRule` outcome.** No rule presently gives `memory.retrieve`/`memory.retrieve_document` an `APPROVED` outcome; deciding whether, and under what confirmation level, to do so is a separate, later, policy-content decision this document does not make (mirroring the Collision Clarification's own identical non-decision, Section 7 of that document). **Gap #54's own live symptom — `KnowledgeSubmission.submit` failing to resolve candidates — is not fixed by this mechanism decision alone.** Resolving *how* the pair can be derived does not, by itself, decide *that* it should be approved.

**How per-record evaluation remains intact:** entirely unaffected. `PermissionFilteredMemoryRetrieval`'s own call pattern — one `PermissionEngine.evaluate` call per direct lookup, one per candidate record in each query-based method's own `filter` (Errata 004 §9) — is untouched; this mechanism changes only what happens inside a single `evaluate()` call once it is reached, never how many times, or for which records, it is called.

**How denied/nonexistent remain indistinguishable:** entirely unaffected. Errata 004 §8's own non-disclosure guarantee (`null` for both absence and denial) lives in `PermissionFilteredMemoryRetrieval`'s own return-shape, structurally downstream of and untouched by anything this mechanism changes inside `DefaultPermissionPolicy`.

**How this combines with the Collision Clarification's own verb-phrase-specific rule mechanism:** the two are complementary facets of the same underlying extension, not competing or overlapping ones. The Collision Clarification's own mechanism (Section 3.2/4 of that document) governs **rule-outcome matching** — which `PermissionPolicyRule` a request's already-derived `(action, resourceType)` pair matches, once one has been derived, distinguishing `memory.retrieve` from `knowledge.retrieve` even though both currently resolve to `(READ, MEMORY)`. This document's own mechanism governs **derivation eligibility** — whether an `(action, resourceType)` pair can be established *at all* without a resolved target Resource, a question that arises *before* rule-matching and is logically independent of it (Section 6 of the Collision Clarification's own Independent Constitutional Review already confirmed this independence directly). Both are naturally expressed as explicit, per-verb-phrase, composition-time configuration on or adjacent to `DefaultPermissionPolicy` — exactly the single location Errata 004 §7 itself already named for "a policy/engine composition decision" — so no second mechanism, second class, or second authority is introduced; this is one coherent extension of the existing, single policy component, applied at two of its own internal steps.

### B. Not Applicable

Since a lawful mechanism is authorised above, this document does not reach Outcome B. Section 5's own analysis identifies precisely what *would* have been missing had the classification/existence separation not held — a genuinely new "protected object class" concept — and confirms it is not needed here.

## 7. A New Finding Beyond the Posed Question — Shared-Decorator Indistinguishability

**Not requested by this task, but surfaced by its own required audit, and directly bearing on "whether all prerequisites are now closed."** `EvidenceIntelligenceInputResolver` and `DefaultKnowledgeCandidateEvaluator` both call `MemoryRetrieval`'s direct-lookup methods (`getEntity`/`getDocument`/`getAssertion`/`getRelationship`) on the **same, single, shared `PermissionFilteredMemoryRetrieval` instance** `ParkerRuntime.kt` constructs once (already established in the Contract Design's own Section 3: "the one shared `PermissionFilteredMemoryRetrieval`... that both `EvidenceIntelligenceInputResolver` and `DefaultKnowledgeCandidateEvaluator` receive — never a second instance"). `PermissionFilteredMemoryRetrieval`'s own methods select the action name (`RETRIEVE_ACTION_NAME`/`RETRIEVE_DOCUMENT_ACTION_NAME`) **based only on the kind of record being retrieved**, never on which of its two callers invoked it — `MemoryRetrieval`'s own interface carries no "consumer identity" concept at all, by design (its own KDoc: `requestingPrincipalId` parameters "exist for auditability only").

**Consequence, independently verified:** even after both the Collision Clarification's own verb-phrase discrimination (distinguishing `memory.retrieve` from `knowledge.retrieve`) and this document's own resolution-derivation mechanism are in place, **there remains no way to give Knowledge Submission's own `memory.retrieve` calls a different policy outcome than Evidence Intelligence's own `memory.retrieve` calls, because the two are structurally identical requests** — same verb phrase, same empty `targetResources`, same shared decorator instance. `requestingPrincipalId` does differ between the two callers today (`DefaultKnowledgeCandidateEvaluator` uses a fixed `SYSTEM_PRINCIPAL_ID = PrincipalId("system.knowledge-memory")`; `EvidenceIntelligenceInputResolver` uses the analysis request's own caller-supplied principal) — but using principal identity to differentiate their policy outcomes would be exactly the caller-specific special case ("if caller == KnowledgeSubmission then allow") this entire governance effort has repeatedly and correctly rejected (Contract Design Section 18; this task's own "Critical constitutional question" instructions), not a lawful discriminator.

**This means: a future policy-content decision to approve `memory.retrieve` (to unblock `KnowledgeSubmission.submit`) cannot, as the system is presently composed, avoid simultaneously approving `EvidenceIntelligenceInputResolver`'s own retrieval — directly contradicting the Contract Design's own Section 14 guarantee** ("`EvidenceIntelligenceInputResolver`'s own currently-correct, deliberately fail-closed retrieval... must remain fail-closed after this blocker is resolved, unless a future, separate, explicitly-reasoned decision changes that"). Resolving this would require a genuinely new architectural decision this document is not authorised to make and does not attempt to design — for example, separately-composed `MemoryRetrieval` decorator instances per consumer (each with its own distinct verb phrase), or an equivalent mechanism — itself a Runtime-composition-tier question, not a resolution-derivation question, and squarely out of this document's own narrow scope ("resolve only this question").

**This is not a revision of the Collision Clarification's own decision** (which correctly resolves the `memory.retrieve` vs. `knowledge.retrieve` collision, a different, orthogonal axis) **and does not require revisiting it** — no genuinely contradictory evidence against that decision was found. It is a third, independent, previously-unidentified prerequisite.
