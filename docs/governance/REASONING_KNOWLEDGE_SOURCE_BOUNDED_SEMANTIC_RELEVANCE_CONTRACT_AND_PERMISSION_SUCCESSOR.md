# ReasoningKnowledgeSource — Bounded Semantic Relevance Contract and Permission Successor

Programme: **Reasoning Context, Bounded Semantic Relevance Contract and Permission Successor for `ReasoningKnowledgeSource`/`DefaultReasoningKnowledgeSource` (adopted).**

## 1. Purpose

This document exists to define the bounded contract and permission-integration surface required to implement, in a later and separately reviewed implementation plan and implementation unit, the single capability the adopted Unit 9.7 Implementation Plan's Section 8 Live-Reasoning Integration gate identifies as required: Bounded Relevance Computation, reusing Unit 9.7's own shared mechanism unchanged, running only as a fallback when `DefaultReasoningKnowledgeSource`'s own existing structural matching finds nothing, over a candidate set Parker has already made eligible and already dereferenced. This document exists because the Reasoning Context Scope Lock's own locked algorithm (its Section 5) and the Reasoning Context Contract Design's own frozen contracts do not, and are not meant to, silently expand to cover a capability outside their own original scope — exactly the reasoning `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 1 already gives for why Unit 9.7 itself, rather than a silent extension of the Unit 9 Contract Design, was required.

## 2. Predecessor/Successor Relationship

This document is a **sibling, not a replacement**, to three predecessor documents, each remaining entirely unedited and in full, unweakened force:

- **The Reasoning Context Scope Lock** — this document elaborates one narrow, additional responsibility (Section 4, below) alongside it, exactly as `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` elaborates the Unit 9 Contract Design without amending it. The Reasoning Context Scope Lock's own Section 6 ("No embeddings, semantic search, or model-based classification, anywhere") and Section 10 ("Semantic search, embeddings, databases, remote services, or indexes") both remain literally true of that document's own text; this document's own later-in-time, expressly-cited adoption — together with `KNOWLEDGE_DISCOVERABILITY_REASONING_CONTEXT_BOUNDED_SEMANTIC_RELEVANCE_SCOPE_LOCK_AMENDMENT.md`'s own proposed qualification of those two provisions — is what would narrowly qualify their practical reach, exactly as CDR-008 already qualifies Memory Core Scope Lock's practical reach without altering its text.
- **The Reasoning Context Contract Design** — this document is a permission and contract *successor* in the sense that it fixes exactly where Bounded Relevance Computation sits relative to that document's own frozen algorithm and error model; it does not amend, reorder, shorten, or introduce any new step, gate tier, or outcome variant into either.
- **The adopted Unit 9.7 Contract and Permission Successor** (`PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md`) — this document does not restate a second, independent mechanism contract; it requires reuse of that document's own Section 4 mechanism contract and Section 3's fourteen conditions unchanged, adapted only for this surface's own dereferenced-content boundary (Section 6, below) and its own structurally distinct algorithm (Reasoning Context Scope Lock Section 5, not Unit 9's own algorithm).

## 3. Complete Authorised Processing Sequence

The following is the complete authorised architecture for any future implementation of this capability inside `ReasoningKnowledgeSource`/`DefaultReasoningKnowledgeSource` — nothing broader is authorised by this contract, regardless of engineering convenience:

1. `DefaultReasoningKnowledgeSource` runs its own existing, frozen ten-step algorithm (Reasoning Context Scope Lock Section 5) unchanged, through structural (substring) matching, exactly as it does today.
2. If structural matching returns one or more relevant candidates, or if any step 1–9 fails or denies, this capability never runs — the existing algorithm's own result stands, unmodified.
3. Only if structural matching completes successfully and returns exactly zero relevant candidates from the full item-level-approved, dereferenced candidate set does Bounded Relevance Computation become eligible to run.
4. The eligible candidate set is exactly the set already produced by steps 1–8 of the existing algorithm — already lifecycle-filtered, already item-level permission-approved, already governed-dereferenced, already `ACTIVE`-Memory-Core-record-status-gated. No broader or additional candidate set is ever assembled for this capability.
5. Each eligible candidate is reduced to an opaque, request-scoped identifier and the single, already-computed, normalized dereferenced content string (Section 6, below) — never the underlying `MemoryCoreRecordReference`, never `evidentialState`/`status`/`StalenessDisclosure`.
6. This reduced candidate set and the query's relevance text are passed to the shared Unit 9.7 relevance mechanism (Section 5, below) — the identical mechanism contract and concrete mechanism `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 4 governs, never a second one.
7. The mechanism returns only opaque identifiers or an ordering over them — never content, never new identifiers.
8. `DefaultReasoningKnowledgeSource` resolves each returned identifier against the exact candidate set it supplied, by direct lookup — never trusting any content the mechanism might additionally, wrongly return.
9. Before constructing any `SafeKnowledgeResultEntry` from a mechanism-surfaced candidate, `DefaultReasoningKnowledgeSource` performs the three-check Pre-disclosure re-verification Section 10 (below) fixes: a fresh `KnowledgeItemPersistence.find` lookup, a fresh `PermissionEngine.evaluate` call for the same item-level intent, and a fresh, second invocation of the identical purpose-bound `MemoryRetrieval.getAssertion`/`getEntity` dereference Pre-computation already performed once — never relying solely on the Pre-computation snapshot from step 4, and never a new capability of any kind.
10. `SafeKnowledgeResultEntry` is constructed in the existing, frozen field order (`content`, `evidentialState`, `status`, `staleness`) from the freshly re-verified `KnowledgeItem` fields and the freshly re-dereferenced Memory Core content step 9's own third check produces — never from the Pre-computation-time snapshot, and never from anything the mechanism returned.
11. `maximumResults` bounding is applied last, exactly as the existing algorithm already does.
12. Semantic/index state created for this computation is request-scoped and fully disposable; nothing survives past the single `recall` call that created it.
13. No persistent secondary index of any kind, for `ReasoningKnowledgeSource` or otherwise, is authorised.
14. Failure of the mechanism fails closed: distinguishable, honestly-propagated (Section 13, below), never a second execution of the structural algorithm, never a stale or partial result presented as complete.
15. The mechanism must be local, in-process, on-device, or otherwise entirely under Parker's own operator/owner control — Model A-Strict condition 13, unweakened.
16. The mechanism's identity, version, and configuration are frozen, disclosed, retrieval-relevant state, shared with `DefaultKnowledgeRetrieval`'s own instance per `KNOWLEDGE_DISCOVERABILITY_REASONING_CONTEXT_CONTRACT_DESIGN_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 12 — upgrades are governed changes, never silent drift.

## 4. Structural-First Fallback Trigger

Bounded Relevance Computation may run only after the Reasoning Context Scope Lock's own frozen, ten-step locked algorithm has, for the given `recall` call, completed every required Pre-computation stage through structural matching — its steps 4 through 9: lifecycle shaping, item-level authorization, governed dereference, and the existing substring match itself — and that structural match has returned a genuine, successful, zero-relevant-candidate outcome over the full eligible, dereferenced candidate set (Section 3, steps 1–3, above). This does not mean the entire ten-step algorithm, including its own final bounding step (step 10), has run; step 10 is reached only after this capability and Pre-disclosure (Section 10, below) have both completed. Fewer-than-`maximumResults` is not zero; one structural match forecloses fallback entirely; permission denial (act-level or item-level), lifecycle exclusion, a non-`ACTIVE` Memory-Core-record-status gate result, or any dependency fault are none of them a fallback trigger — each of those already produces its own existing, correct outcome under the unmodified algorithm, and this capability never runs on any of those paths.

## 5. Lifecycle and Permission Ordering

This document does not reorder, parallelise, or collapse any step of the Reasoning Context Scope Lock's own frozen algorithm (its Section 5) or the underlying Permission Enforcement Mechanism Clarification's evaluation order; it adds no new step to either and instead consults them only after they have already completed their own required Pre-computation stages through structural matching, for the given request (Section 3, Section 4, above) — never after the frozen algorithm's own final bounding step. Immediately before any `SafeKnowledgeResultEntry` is constructed from a relevance-mechanism-surfaced identifier, `DefaultReasoningKnowledgeSource` performs the three-check Pre-disclosure re-verification Section 10 (below) fixes for that identifier, freshly, against current state — never relying solely on the Pre-computation snapshot (Section 3, step 9, above). This is the successor relationship named in Section 2: this document is where the Reasoning Context Scope Lock's own frozen algorithm and Bounded Relevance Computation's own fallback trigger are jointly, precisely fixed relative to one another.

## 6. Lawful Dereferenced-Content Handling and Minimum-Content Reduction

`DefaultReasoningKnowledgeSource`, unlike `DefaultKnowledgeRetrieval`, lawfully dereferences Memory Core content today, through its own purpose-bound `MemoryRetrieval` view, exactly as the Reasoning Context Scope Lock's own Section 5 (steps 7–8) already authorises. This document does not authorise any additional dereference, any additional Memory Core call, or any additional field, beyond what that existing, frozen algorithm already resolves for structural matching, to cross **into the relevance mechanism**. The minimum-content reduction before semantic computation is fixed exactly as `KNOWLEDGE_DISCOVERABILITY_REASONING_CONTEXT_CONTRACT_DESIGN_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 3 already determines: the single, already-computed, already-normalized `content: String` value the existing algorithm produces per candidate, and nothing else — not the `MemoryCoreRecordReference`, not its reference kind, not `evidentialState`, `status`, or `StalenessDisclosure`. The relevance mechanism never receives a `KnowledgeItem`, a `MemoryCoreRecordReference`, or any Memory Core identifier of any kind — only the opaque per-request token (Section 7, below) and this one bounded content string. This input-side restriction is distinct from, and does not foreclose, `DefaultReasoningKnowledgeSource`'s own separate, later, Pre-disclosure re-dereference of a mechanism-surfaced candidate (Section 9, Section 10, below) — that re-dereference is Parker's own internal operation on its own already-held candidate, performed entirely outside the relevance mechanism's own visibility, and is a second invocation of the identical governed call this paragraph already describes, never a new or wider one.

## 7. Opaque Request-Token Boundary

The relevance mechanism never receives a candidate's permanent `KnowledgeId`, Memory Core identifier (`AssertionId`/`EntityId`), provenance reference, evidence reference, lifecycle history, permission state, evidential state, or status. Candidates are identified to the mechanism solely by opaque, request-scoped, unlinkable tokens minted fresh for each `recall` call — mirroring `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 3, condition 6, exactly. `DefaultReasoningKnowledgeSource` alone resolves every returned token back to its own already-held candidate; a token that fails to resolve, or resolves outside the exact set supplied for the current request, is an integrity fault, rejected outright, treated identically to an unauthorised candidate (Section 8, below).

## 8. Shared Unit 9.7 Mechanism Reuse

This document requires that any implementation reuse, unchanged, the identical relevance mechanism contract `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 4 fixes, and the identical concrete mechanism Unit 9.7.1's contract types and Unit 9.7.3's own semantic-fitness-gated selection (the adopted Unit 9.7 Implementation Plan Section 13.1) ultimately produce. This document defines no embedding engine, no QMD adapter, no ranking algorithm, and no semantic configuration authority of its own — it defines only the *orchestration* fixing where that already-governed mechanism is invoked inside `DefaultReasoningKnowledgeSource`'s own algorithm (Sections 3–5, above), mirroring how this codebase already, deliberately duplicates `isRetrievable`, `disclosureFor`, and the two-tier permission-gate pattern between `DefaultKnowledgeRetrieval` and `DefaultReasoningKnowledgeSource` today — an orchestration-level duplication precedented in this exact codebase, never a semantic-mechanism-level one.

## 9. Canonical Re-Resolution

Every candidate surfaced by the relevance mechanism is re-resolved by `DefaultReasoningKnowledgeSource` against its own already-held, canonical candidate set — the same `KnowledgeItem` identity the mechanism was given a token for, never a competing or mechanism-supplied representation, and never a candidate outside the exact set originally supplied. That resolution is completed, and the content ultimately disclosed is established, only through the three-check Pre-disclosure re-verification Section 10 (below) fixes — never through the mechanism's own output, and never through a new or widened Memory Core operation; the fresh, second Memory Core dereference Section 10's third check performs is a lawful, already-governed operation, not a new capability, and its result — not any earlier snapshot — is what Parker treats as canonical at disclosure time. Memory Core, and Knowledge Memory's own canonical persistence downstream of it, remain Parker's sole authoritative system of record; this document does not create, and no implementation of it may become, a persistent parallel or secondary source of canonical truth (CDR-008 Mandatory Invariant 12).

## 10. Fresh Pre-Disclosure Re-Verification

Immediately before constructing any `SafeKnowledgeResultEntry` from a relevance-mechanism-surfaced candidate — never for the full candidate pool, only for candidates the mechanism actually surfaces — `DefaultReasoningKnowledgeSource` performs exactly three checks, each a second invocation of an operation Pre-computation already performed once, never a new Memory Core, `KnowledgeItemPersistence`, or `PermissionEngine` capability:

1. **`KnowledgeItem` currentness.** A fresh `KnowledgeItemPersistence.find(knowledgeId)` lookup, confirming the item still exists and remains eligible under `KnowledgeItem.status`.
2. **Permission currentness.** A fresh `PermissionEngine.evaluate` call for the same item-level intent Pre-computation already constructed, confirming current authorisation.
3. **Memory Core currentness and content.** A fresh, second invocation of the identical purpose-bound `MemoryRetrieval.getAssertion`/`getEntity` call `resolveContent`'s own existing dereference step already makes once. Because that call returns the whole referenced record, not a status-only projection, this single call simultaneously establishes whether the record still exists, whether its `MemoryCoreRecordStatus` is still `ACTIVE` (a non-`ACTIVE` or absent result excludes the candidate — `DISPUTED`, `SUPERSEDED`, `ARCHIVED`, `DELETED`, and "no such record" all collapse into the identical "excluded" outcome the existing algorithm's own Pre-computation dereference already produces), and, only if still `ACTIVE`, its current content.

Any of the three checks failing excludes the candidate outright — never disclosed, never substituted. This document does not claim an ability to detect that content changed between Pre-computation and Pre-disclosure as its own distinguishable signal — it claims only that whatever is disclosed is always current as of Pre-disclosure, because check 3 cannot be performed without receiving the record's then-current content. Pre-computation and Pre-disclosure are both mandatory and are not alternatives to each other, mirroring `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 6's own closing statement exactly.

## 11. `SafeKnowledgeResultEntry` Authority Remains with Parker

`DefaultReasoningKnowledgeSource` alone constructs every `SafeKnowledgeResultEntry`, in the existing frozen field order, from its own freshly-re-verified `KnowledgeItem` state (Section 10, checks 1–2) and its own freshly re-dereferenced Memory Core content (Section 10, check 3) — never from the Pre-computation-time snapshot, and never from anything the relevance mechanism returns beyond an opaque identifier or ordering. The relevance mechanism cannot construct, partially construct, or influence the content of a `SafeKnowledgeResultEntry` in any way beyond determining which already-eligible candidates are surfaced.

## 12. No `ReasoningContext` Rendering Authority

This capability has no authority over, and does not participate in, `DefaultReasoningContextAssembler`'s own rendering of `SafeKnowledgeResultEntry` into `ReasoningContext` text (`renderKnowledgeEntry`, the Reasoning Context Scope Lock's own Section 6 rendering/escaping contract). Rendering, escaping, and `ReasoningContext` composition remain entirely unchanged, unaffected, and outside this document's own scope.

## 13. Fail-Closed Behaviour

| Failure | Constitutional requirement |
|---|---|
| Mechanism unavailable | Distinguishable, honestly-propagated outcome; the already-computed, successful, zero-result structural outcome (Section 4, above) stands as the final result, without re-executing the Scope Lock's own structural algorithm — never silently omitted |
| Timeout | Treated identically to mechanism unavailable |
| Relevance computation fails | Same as above; never presented as though the mechanism ran successfully and found nothing |
| Malformed ranking result | Fail loudly (reject the whole result), never silently coerce to an empty or partial list |
| Mechanism returns candidate content instead of identifiers | Rejected as an integrity fault; content returned by the mechanism is never trusted, rendered, or substituted for Parker's own canonical, already-dereferenced content |
| Returned content differs from the content `DefaultReasoningKnowledgeSource` supplied | Rejected as an integrity fault, treated identically to an unauthorized candidate |
| Unknown or unauthorized returned identifier | Rejected as an integrity fault — never trusted merely because it resembles an authorized one |
| Duplicate identifier | De-duplicated before bounding; never consumes more than one of `maximumResults`' slots |
| Too many results returned | The mechanism's own limit is a performance hint only; `DefaultReasoningKnowledgeSource`'s own bounding step is authoritative regardless |
| Request-token collision or stale/cross-request token | Rejected as an integrity fault; a token's validity never outlives the single `recall` call that issued it |
| Canonical `KnowledgeItem` no longer exists or is no longer eligible (e.g. retired) at Pre-disclosure | Caught by Section 10 check 1 (fresh `KnowledgeItemPersistence.find`); excluded, never disclosed |
| Permission no longer approved at Pre-disclosure | Caught by Section 10 check 2 (fresh `PermissionEngine.evaluate`); excluded, never disclosed |
| Referenced Memory Core record no longer exists, or its `MemoryCoreRecordStatus` is no longer `ACTIVE` (covers `DISPUTED`, `SUPERSEDED`, `ARCHIVED`, `DELETED`, and "no such record" alike — all collapse into the same outcome) at Pre-disclosure | Caught by Section 10 check 3 (fresh, second `MemoryRetrieval.getAssertion`/`getEntity` invocation); excluded, not substituted |
| Referenced Memory Core content differs from the Pre-computation-time snapshot the relevance mechanism was shown | Not a distinguishable failure; not detected or reported as "changed" — Section 10 check 3 always yields the current content, which is what `SafeKnowledgeResultEntry` uses regardless of whether it differs from the earlier snapshot |
| Mechanism attempts to write/mutate canonical persistence, dereference additional Memory Core content, or enumerate beyond the supplied set | Architecturally impossible, not merely prohibited by policy — the interface or process boundary given to the mechanism must make this structurally impossible |

Pre-computation authorisation (Section 3, above) and Pre-disclosure re-verification (Section 10, above) are both mandatory and not alternatives to each other.

## 14. Prohibited Behaviours

Consolidated from Sections 3–13, above: this capability may never become or contribute to canonical memory, an alternative memory store, or a secondary source of truth; determine eligibility, permission, lifecycle/status, or evidential-state classification; construct `SafeKnowledgeResultEntry` from mechanism-supplied content, or render `ReasoningContext`; persist beyond a single `recall` call; run on a candidate before that candidate has completed Pre-computation under the existing algorithm; run when structural matching found one or more results or itself failed; dereference additional Memory Core content beyond Section 6's own minimum-content boundary; enumerate or request candidates beyond the closed set the existing algorithm supplied; write or mutate canonical persistence; use a remote or cloud-hosted mechanism; use a second, independently-selected or independently-configured semantic mechanism (Section 8, above); or extend, by its own force or by analogy, to `WorldModelSource`, `ConversationHistorySource`, Evidence Custodian, `PermissionEngine`, Memory Core, or `DefaultKnowledgeRetrieval` itself.

## 15. Determinism/Version/Configuration Requirements

Identical query, identical canonical state, and identical frozen mechanism identity/version/configuration must together produce an identical result, including identical ordering, on repeated invocation — restated here as a binding requirement, incorporated by reference from `KNOWLEDGE_DISCOVERABILITY_REASONING_CONTEXT_CONTRACT_DESIGN_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 11. Because the mechanism instance is shared with `DefaultKnowledgeRetrieval` (Section 8, above), a mechanism upgrade is a single governed change affecting both surfaces identically, never a divergent one.

## 16. Required Verification Properties

A later implementation plan and implementation unit for this capability must be able to demonstrate, before completion is claimed, that the implementation satisfies each of the following — stated here as governance-level verification criteria, not as test code:

1. **Determinism.** Identical query, identical canonical state, and identical frozen mechanism identity/version/configuration produce an identical result, including identical ordering, on repeated invocation.
2. **Fallback precision.** The capability never runs when structural matching returns one or more results, and never runs when any earlier step of the existing algorithm fails or denies; it runs only on a genuine, successful, zero-result structural outcome.
3. **Minimum-content boundary.** The relevance mechanism demonstrably receives only the opaque token and the single normalized content string per candidate — never a `KnowledgeId`, `MemoryCoreRecordReference`, `evidentialState`, `status`, or `StalenessDisclosure`.
4. **Fail-closed completeness.** Every row of Section 13's table produces its stated outcome under deliberate fault injection, with no silent degradation to a partial or stale result presented as complete.
5. **No authority transfer.** Every responsibility other than fallback relevance ordering itself is independently verifiable as unchanged from today's `DefaultReasoningKnowledgeSource` behaviour.
6. **Shared-mechanism proof.** The mechanism instance (or an identically-configured, identically-versioned equivalent) used by this capability is the same one Unit 9.7 governs for `DefaultKnowledgeRetrieval` — not a second, independently-configured instance.
7. **Architectural inability, not policy promise.** The mechanism's own interface or process boundary is inspectable and demonstrates it structurally cannot reach canonical persistence, dereference additional Memory Core content, or enumerate beyond its supplied candidate set.
8. **`ReasoningContext` rendering non-involvement.** The implementation demonstrably makes no change to `renderKnowledgeEntry` or any other Reasoning Context Scope Lock Section 6 rendering/escaping behaviour.
9. **Memory Core non-involvement beyond the existing dereference.** The implementation demonstrably introduces no new *kind* of Memory Core call, dependency, or behavioural change beyond the existing, frozen dereference the Reasoning Context Scope Lock's own Section 5 already authorises — a second invocation of that identical call, for Section 10's own Pre-disclosure re-verification, is expected and required, never a new one.
10. **Pre-disclosure freshness proof.** Each of Section 10's three checks is independently verifiable: a fresh `KnowledgeItemPersistence.find` call, a fresh `PermissionEngine.evaluate` call, and a fresh, second `MemoryRetrieval.getAssertion`/`getEntity` call each genuinely execute a second time, against current state, for every mechanism-surfaced candidate before disclosure — never merely re-reading the Pre-computation snapshot.
11. **Live-reasoning reachability proof.** Unlike Unit 9.7's own analogous property (which cannot make this claim, per the adopted Unit 9.7 Implementation Plan's own Section 4.2/4.3), an implementation of this capability must demonstrate the real, same-runtime end-to-end proof the Reasoning Context Scope Lock's own Section 2 already requires — inspecting real `ReasoningContext.entries` or the real assembled model prompt directly — now genuinely exercising Bounded Relevance Computation on a structurally-dissimilar paraphrase of a promoted proposition, mirroring the `aadd596` fixture's own demonstrated scenario.
