# Knowledge Discoverability and Governed Retrieval into Reasoning Context — Bounded Semantic Relevance Scope Lock Amendment

Programme: **Reasoning Context Scope Lock, Bounded Semantic Relevance Amendment (adopted).**

## 1. Capability Authorised

This amendment would authorise exactly one capability: **Bounded Relevance Computation inside `ReasoningKnowledgeSource`/`DefaultReasoningKnowledgeSource`**, reusing — never re-implementing — the same mechanism contract and concrete mechanism already governed for Knowledge Retrieval by the adopted Unit 9.7 package (`PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 4). It is a request-scoped, subordinate, replaceable computation that orders or reduces an already Parker-authorised, already-eligible, closed candidate set the Reasoning Context Scope Lock's own locked algorithm (its Section 5) has already produced, and does nothing else. It authorises no second semantic mechanism, no library, model, or product by name, and no capability broader than this sentence.

## 2. Problem Solved

Parker's live Reasoning Context — the only path a running conversation actually consults, per `DefaultReasoningContextAssembler`'s wiring to `reasoningKnowledgeSource` in `src/composition/ParkerRuntime.kt` — can hold a genuinely promoted, canonical proposition that a later, structurally-dissimilar paraphrase of the same request fails to recall, because `DefaultReasoningKnowledgeSource.recall()`'s only relevance mechanism today is case-insensitive substring matching against dereferenced Memory Core content (Reasoning Context Scope Lock Section 6; demonstrated against the real, running `ParkerRuntime` in commit `aadd596`, `ParkerRuntimeReasoningContextIntegrationTest.kt`). The adopted Unit 9.7 package already remedies the structurally analogous defect for `DefaultKnowledgeRetrieval` — but the adopted Unit 9.7 Implementation Plan's own Section 4.2/4.3 establishes, from the adopted governance's own text, that `DefaultKnowledgeRetrieval` is not consumed anywhere in the live reasoning path, and that `ReasoningKnowledgeSource` is the correct, deliberately separate, live-reasoning-facing surface (Reasoning Context Contract Design Decision-Register item 3, RESOLVED; Boundary Review Section 3, "`DefaultKnowledgeRetrieval` or its successor"). This amendment exists solely to extend the same, already-governed remedy to the surface that actually reaches live reasoning, and for no broader purpose.

## 3. Case 3 Determination Preserved — No Cutover to `KnowledgeRetrieval`

This amendment does not, and could not lawfully, propose cutting Reasoning Context over to consume `KnowledgeRetrieval`/`DefaultKnowledgeRetrieval` directly in place of `ReasoningKnowledgeSource`. The adopted Unit 9.7 Implementation Plan's Section 4.3 establishes, from the Reasoning Context Contract Design's own Decision-Register item 3 (RESOLVED) and the Boundary Review's own Section 3 text, that the two-surface architecture is a deliberate, already-adopted design decision: widening `KnowledgeRetrieval` itself to carry content "reopens the frozen Unit 9 `never copies Memory Core content` guarantee for every current and future consumer, not only Reasoning Context," and a new, narrow, additive `ReasoningKnowledgeSource` contract was adopted instead, specifically, as the narrow, additive, content-carrying surface Reasoning Context is architecturally required to use. This amendment reopens neither that determination nor Decision-Register item 3; it extends Bounded Relevance Computation to the surface that determination already names as correct.

This amendment also does not disturb the reason `ReasoningKnowledgeSource` exists as a structurally separate class from `DefaultKnowledgeRetrieval`, duplicating rather than sharing its structural-match/lifecycle/permission-gate logic by the Reasoning Context Contract Design's own explicit, adopted design choice (each duplicated method's own KDoc states this reasoning). This amendment does not merge, unify, or share code between the two classes beyond the one shared element it requires: the Unit 9.7 relevance mechanism contract and concrete mechanism themselves (Section 11, below).

## 4. What Remains Authoritative

Parker retains, unconditionally and without exception, exactly as the Reasoning Context Scope Lock's own Sections 3–8 already fix: Memory Core as the sole authority for remembered proposition content and provenance; `KnowledgeItem` as the authority for promotion and evidential state; query-time governed dereferencing as the only route to content, never cached or persisted; every permission decision, in content and enforcement, exclusively through `PermissionEngine`; the fixed `SafeKnowledgeResultEntry` field order and construction; and exclusive `ReasoningContext` rendering. Nothing this amendment would authorise creates, or can become, a parallel or secondary source of canonical truth, and nothing in it grants the relevance mechanism access to raw Memory Core content beyond the single, already-dereferenced, per-candidate content string the locked algorithm's own Section 5 step 8/9 already produces today.

## 5. What Semantic Relevance May Do

The mechanism this amendment would authorise may, and may only: accept the authorised query's relevance text and a closed, Parker-supplied set of already-eligible, already-dereferenced candidates, each reduced to an opaque per-request identifier and the single normalized content string `DefaultReasoningKnowledgeSource`'s own existing dereference step already computes (Section 6, below, fixes the exact boundary); and return an ordering or subset of those same identifiers. Nothing else is a permitted output — mirroring `PROGRAMME_3_KNOWLEDGE_MEMORY_BOUNDED_SEMANTIC_RELEVANCE_SCOPE_LOCK_AMENDMENT.md` Section 5 exactly, adapted only for the dereferenced-content boundary this surface, unlike `DefaultKnowledgeRetrieval`, lawfully operates over.

## 6. What Semantic Relevance May Not Do

Candidate discovery under this amendment does not, and may never: establish truth; create, modify, or delete canonical knowledge or Memory Core content; alter provenance; determine or influence a permission decision; determine or influence lifecycle/status or evidential-state classification; construct, in whole or in part, a `SafeKnowledgeResultEntry`; render, compose, or influence `ReasoningContext` text; persist beyond the single request that created it; expand, substitute into, or otherwise alter the candidate set Parker supplied; itself dereference any Memory Core content of any kind, at any time — every dereference remains Parker's own, exclusively, both before the mechanism runs and, per Section 9 (above) and `KNOWLEDGE_DISCOVERABILITY_REASONING_CONTEXT_CONTRACT_DESIGN_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 9, again immediately before disclosure; or redefine `ReasoningKnowledgeSource`'s canonical retrieval semantics in any way. Every one of these is architecturally foreclosed, not merely discouraged, mirroring `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 9.

## 7. Permission Boundaries

`PermissionEngine`'s sole authority over every permission decision is untouched. The mechanism this amendment would authorise runs strictly after the Reasoning Context Scope Lock's own frozen, ten-step locked algorithm (its Section 5) has completed every required Pre-computation stage through structural matching — lifecycle shaping, item-level authorization, governed dereference, and the existing substring match itself — and that structural match has completed successfully with exactly zero relevant candidates; never before, never in place of, and never reordering any of those steps, and never implying the algorithm's own final bounding step (its step 10) has already run. Parker re-verifies permission, current lifecycle/status, and Memory Core record currentness and content, freshly, immediately before any disclosure, never relying solely on the Pre-computation snapshot — the exact three-check Pre-disclosure rule `KNOWLEDGE_DISCOVERABILITY_REASONING_CONTEXT_CONTRACT_DESIGN_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 9 fixes, itself extending the same Pre-computation/Pre-disclosure distinction the adopted Unit 9.7 package already establishes (`PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 5). Permission enforcement is fail-closed: any non-`APPROVED`/`APPROVED_WITH_CONFIRMATION` outcome, at either gate tier, forecloses the candidate before it is ever visible to the relevance mechanism.

## 8. Fail-Closed Expectations

Every failure mode — mechanism unavailable, timeout, malformed output, an unknown, unauthorised, altered, duplicate, or stale/cross-request identifier, a permission or lifecycle change during computation, or an attempt to write canonical persistence, dereference additional Memory Core content, or enumerate beyond the supplied set — must propagate as a distinguishable, honestly-disclosed outcome, never silently coerced into an empty or partial result presented as complete. The full, binding fail-closed table is fixed at `PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 6 and restated, adapted only for this surface's own error model, in `REASONING_KNOWLEDGE_SOURCE_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 13; this Scope Lock amendment incorporates both by reference rather than duplicating them a third time.

## 9. Provenance and Identity Preservation

The relevance mechanism never sees, assigns, or discloses a candidate's permanent `KnowledgeId`, Memory Core identifier, provenance reference, evidence reference, lifecycle history, evidential state, or permission state. It identifies candidates solely by opaque, request-scoped, unlinkable tokens, exactly as `PROGRAMME_3_KNOWLEDGE_MEMORY_BOUNDED_SEMANTIC_RELEVANCE_SCOPE_LOCK_AMENDMENT.md` Section 9 already requires for the Knowledge Retrieval surface. Parker alone resolves every returned token back to its own canonical `KnowledgeItem`, by direct lookup; a token that fails to resolve, or resolves outside the exact set Parker supplied, is an integrity fault, rejected outright — never silently substituted. A token that does resolve is then subject to the fresh, second, already-governed Memory Core dereference `KNOWLEDGE_DISCOVERABILITY_REASONING_CONTEXT_CONTRACT_DESIGN_BOUNDED_SEMANTIC_RELEVANCE_AMENDMENT.md` Section 9 fixes — the identical dereference operation Pre-computation already performed once, invoked a second time, never a new Memory Core capability — before any disclosure.

## 10. Exclusions and Non-Goals

This amendment does not authorise: a second semantic mechanism, embedding engine, ranking implementation, or semantic configuration authority independent of the one Unit 9.7 already governs; remote or cloud-hosted relevance processing; a persistent semantic index of any kind; a parallel or secondary canonical store; semantic, ranked, or scored retrieval for any Reasoning Context input other than `ReasoningKnowledgeSource` itself (`WorldModelSource` and `ConversationHistorySource` are explicitly untouched, per the Reasoning Context Scope Lock's own Section 3 item 11); a general redesign of Reasoning Context, `DefaultReasoningContextAssembler`, or any of the Reasoning Context Scope Lock's own Sections 1–12, 14–15; any production implementation by its own adoption; or any change to Memory Core, Evidence Custodian, `PermissionEngine`'s own sole authority, or CDR-008. Consistent with Model A-Strict condition 13, the mechanism this amendment would authorise must be local, in-process, on-device, or otherwise entirely under Parker's own operator/owner control; no remote, cloud-hosted, or third-party-network-reachable relevance processor is authorised, and no candidate content or query text may cross any network boundary the operator does not control.

## 11. Relationship to Unit 9.7 — Shared Mechanism, Not a Second One

This amendment implements, without reopening or re-litigating, the adopted Unit 9.7 package's own Model A-Strict architecture and mechanism contract in full, extended to this surface. It requires that any future implementation reuse Unit 9.7's own relevance mechanism contract (`PROGRAMME_3_UNIT_9_7_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` Section 4) and the concrete mechanism ultimately selected and implemented under Unit 9.7.3's own semantic-fitness gate (the adopted Unit 9.7 Implementation Plan Section 13.1) — unchanged — never a second, independently selected or independently configured embedding engine, adapter, or ranking implementation. This amendment authorises only new *orchestration* at the `ReasoningKnowledgeSource` boundary (Section 5, invoking the shared mechanism after this surface's own locked algorithm completes); it authorises no new semantic mechanism *implementation* of any kind. Where this amendment's own text and the adopted Unit 9.7 package could be read to diverge on the mechanism's own required properties, the adopted Unit 9.7 package controls, and that divergence is itself a defect to be corrected before adoption.

## 12. Explicit Prohibition on Unintended Architectural Expansion

No sentence in this amendment may be cited as authorising anything beyond Section 1's single capability. In particular: this amendment creates no general "relevance" or "ranking" responsibility for `ReasoningKnowledgeSource` beyond the precise, zero-result-only fallback Section 7 and `REASONING_KNOWLEDGE_SOURCE_BOUNDED_SEMANTIC_RELEVANCE_CONTRACT_AND_PERMISSION_SUCCESSOR.md` fix; no authority to cut Reasoning Context over to `KnowledgeRetrieval` (Section 3, above); no precedent-by-analogy for any other Reasoning Context input (`WorldModelSource`, `ConversationHistorySource`) or any other component's own Scope Lock; and no implicit authorisation of any future broadening (persistent indexing, remote processing, additional subsystems, `getDocument`/`ToDocument` reach) without that broadening's own, separate, dedicated governance review. A future implementer or reviewer who reads this amendment as authorising more than Section 1 states has misread it.
