# Plan Candidate Generation — Contract Design

## Status

**Contract Design only. No Kotlin is implemented, proposed as a diff, or
changed by it, beyond illustrative signatures used to state a design
decision precisely.** Neither `src/` nor `tests/` is touched. This
document does not produce a Scope Lock and authorises no implementation —
it determines whether Scope Lock may begin, and on what terms.

**Repository position.** Branch `main`. Current implementation includes
Sprint 11 Reasoning Context, the Reasoning-to-Planning Handoff, and
`GoalPlanningHandoffCoordinator`. Latest verified commit: `b5bcc93`. Every
prior Governance Review, Contract Design, and Scope Lock — including
`docs/architecture/PLAN_CANDIDATE_GENERATION_GOVERNANCE_REVIEW.md` (this
Unit's own immediate predecessor, approved) — is treated as settled
architecture and is not reopened here.

**Charter, restated exactly.** The primary purpose of this document is
**not** to define methods. It is to define the information boundary: what
a Candidate Generator may legitimately receive in order to produce one or
more `PlanCandidate`s. The public contract (Section 4) is designed only
after that boundary is settled (Sections 1–3), not before.

---

## Architectural Priority — the One Question This Unit Answers First

**What is the minimum information a Candidate Generator is legitimately
allowed to receive in order to produce one or more `PlanCandidate`s?**

Answered in Section 1, before any interface, ownership, or placement
decision is made. Every later section depends on that answer; none of
them revises it.

---

## Section 1 — Information Boundary

For each candidate input, this section determines mandatory, optional, or
prohibited, and why. The governing principle throughout is AD-011
(Context Is Reference-Based): "The Planner Runtime, Task Manager Runtime,
and Agent Runtime each hold their own transient Context... built from
references... never by copying another component's internal state, and
never by directly owning Memory or World Model state," together with
`PlannerRuntimeSpecification.md` Section 9's identical rule for Planning
Context specifically: "Planning Context is not Task Context, and is not
Agent Context... each is scoped to, and owned by, its own runtime... and
each references the others only by ID... never by direct read or write
access to another's internal state." Candidate Generation is, at minimum,
as bound by this rule as the Planner Runtime it feeds — it inherits, not
escapes, this discipline.

### Goal text — **Mandatory**

The entire reason Candidate Generation exists. Arrives already inside
`PlanningRequest.goal`, not as a separately-passed `String` — see
`PlanningRequest`, below.

### PlanningRequest — **Mandatory**

The sole input object. `PlanningRequest` (`src/contracts/PlanDecision.kt`,
lines 214–226) already carries `goal: String`, `initiatingPrincipalId:
PrincipalId`, `correlationId: String`, `source: RequestOrigin`, `priority:
RequestPriority`, `planningSessionId: PlanningSessionId` — already
constructed, already validated (`goal`/`correlationId` non-blank), and
already the settled, canonical "start of a Planning Session" object per
`PLANNER_RUNTIME_CONTRACT_DESIGN.md` Type 6. `PlanningRequest`'s own
correction history is directly on point: `candidates` was deliberately
removed from this type specifically so that "candidates are generated by
planning, not supplied by callers alongside the request that starts it" —
the same document already anticipated an external mechanism receiving
exactly this object to do exactly this job. Passing `PlanningRequest`
whole, rather than decomposing it into separate `goal`/`correlationId`/
`initiatingPrincipalId` parameters, avoids inventing a second,
divergence-prone carrier for the same facts.

### Turn — **Prohibited**

`Turn` (`turnId`, `conversationId`, `message`, `receivedAt`) is
`ConversationEngine`'s own concept, not Planner-owned. Passing it directly
into Candidate Generation would hand a Planner-adjacent component direct
read access to another runtime's internal record, violating AD-011.
Whatever from `Turn` is legitimately needed (`correlationId`, the
initiating identity) is already present on `PlanningRequest` — `Turn`
itself carries nothing further that this boundary is authorised to use.

### CorrelationId — **Mandatory, already embedded, not a separate parameter**

Present as `PlanningRequest.correlationId: String` (already unwrapped from
`CorrelationId` by `GoalPlanningHandoffCoordinator`, per the settled
Reasoning-to-Planning Handoff). No separate `CorrelationId` parameter is
introduced — one already exists on the mandatory input.

### Authenticated Principal — **Optional / reference-only**

`PlanningRequest.initiatingPrincipalId: PrincipalId` is already present
(mandatory, as part of `PlanningRequest`). Candidate Generation may read
this identifier — for example, to label `anticipatedPermissionActions` in
a way that is meaningful for a specific Principal — but **must never
resolve, evaluate, or status-check identity itself**. Identity resolution
remains exclusively `PlannerRuntime.plan()`'s own, already-implemented job
(`IdentityService.resolve`, existence-check only, per
`IMPLEMENTATION_GAPS.md` #37, unrelated to and unchanged by this Unit).
Reading an identifier that is already present is not the same as
resolving it — the distinction is deliberate and binding.

### Runtime metadata — **Prohibited**

No such contract concept currently exists anywhere in `src/contracts` or
`src/interfaces` for Planner-adjacent components (no Planner Policy
configuration object, no environment/deployment descriptor). Introducing
one here, speculatively, for no concrete identified need, would be scope
creep beyond this Unit's charter. `PlannerRuntimeSpecification.md`
Section 4 names "Planner Policy" as a future bounded-configuration
concept (e.g. a maximum candidate count) — if and when that is designed,
it is separately chartered work (Section 9), not introduced by this
document.

### Conversation History — **Prohibited, for this Unit**

Full transcript/turn history is owned by `ConversationEngine` and its
history sources, consulted today only by `ReasoningContextAssembler` on
`ReasoningProvider`'s behalf. Giving Candidate Generation direct access
would both violate AD-011 and exceed what is needed to decompose an
already-identified Goal — Candidate Generation's job (per the approved
Governance Review, Section 4 there) begins only after a Turn has already
been classified as a `Goal`; it does not need to re-derive that
classification from raw history. If conversation-derived facts are ever
legitimately needed, they must arrive as a bounded, reference-based
Planning Context (Section 3, below) — not as raw history handed across
this boundary.

### Memory Source — **Prohibited, for this Unit**

No Memory read path exists anywhere in the planning boundary today —
`PlannerRuntimeSpecification.md` Section 3's own Non-Goals: "Memory
implementation... The Planner Runtime reads and writes no long-term
memory." Introducing one for Candidate Generation specifically, ahead of
any dedicated Memory-into-Planning integration Unit, would pre-empt a
larger, separately-chartered decision and directly contradicts this
Unit's own exclusion ("do not modify persistent memory").

### World Model Source — **Prohibited, for this Unit**

Identical reasoning to Memory Source. `PlannerRuntimeSpecification.md`
Section 3: "World Model implementation... untouched. Planning Context...
is explicitly not a World Model." No existing read path; none introduced
here.

### Reasoning Context — **Prohibited**

This is the central determination this Unit exists to make, resolved
fully in Section 3 below: `ReasoningContext` does not cross this boundary,
under any circumstance, permanently — not merely deferred pending a
future decision.

## Section 2 — Ownership

Settled at the Governance Review level (Section 14 there) and confirmed,
not re-litigated, here, now that Section 1's boundary makes the
consequences of that determination concrete.

**`PlannerRuntime` — excluded.** Unchanged conclusion.
`PlannerRuntime.plan(request, candidates)`'s already-accepted signature
takes `candidates: List<PlanCandidate>` as an externally-supplied
parameter specifically because `PLANNER_RUNTIME_CONTRACT_DESIGN.md`
already decided candidate generation happens outside `plan()`, not inside
it. Section 1's minimal information boundary (`PlanningRequest` only)
changes nothing about this — if anything, it reinforces it: a component
whose entire legitimate input is a single, already-validated
`PlanningRequest` has no architectural need to live inside a stateful,
identity-resolving, event-publishing runtime like `InMemoryPlannerRuntime`.

**`GoalPlanningHandoffCoordinator` — excluded, as currently scoped, and
not revised by this Unit.** Its own KDoc's "one dependency, structural
guarantee" convention is the same convention every coordinator in this
codebase relies on (`ConversationTurnReasoningCoordinator`,
`ReplyDeliveryCoordinator`, `ConversationReplyCoordinator`). Section 1's
boundary determination means a `CandidateGenerator` would need only a
`PlanningRequest` — the exact object `GoalPlanningHandoffCoordinator`
already constructs — which makes it structurally *possible* for that
class to also hold a generator dependency without needing anything else
new. Whether it *should* is a placement question, not an ownership
question, and is addressed in Section 3. This Unit does not modify
`GoalPlanningHandoffCoordinator` (explicit exclusion) and this
determination does not require modifying it either.

**A dedicated `PlanCandidateGenerator` — recommended, confirmed.** Named
`PlanCandidateGenerator`, not the more generic "Candidate Generator" used
informally in the Governance Review, to match this codebase's own existing
naming family (`PlanCandidate`, `PlanDecision`, both "Plan"-prefixed,
distinct from the "Planning"/"Planner"-prefixed request/runtime types).
Modelled directly on the two existing precedents for exactly this kind of
seam:

- `ReasoningProvider` (`src/interfaces/ReasoningProvider.kt`) — a single
  `suspend` method, model-independent, pure callee, holds no authority.
- `PlanDecision` (`src/contracts/PlanDecision.kt`) — a single `suspend`
  method, model-independent (per its own Contract Design's AD-010
  justification), consumes and produces only already-approved types.

`PlanCandidateGenerator` is architecturally the same *kind* of component —
interpreting an already-validated input and producing a structured
judgment, without holding executable authority — not a sequencing
coordinator and not a stateful runtime. Given Section 1's boundary, its
entire input surface is one object it does not construct
(`PlanningRequest`); it needs no other dependency to do its job.

**No other runtime component is a serious candidate**, unchanged from the
Governance Review's own conclusion (Section 3.4 there) — restated, not
re-argued.

## Section 3 — Placement (the most important question in this Unit)

**Resolution: `GoalPlanningHandoffCoordinator` should remain intentionally
ignorant of `ReasoningContext` — permanently, not provisionally, and not
because of an accident of the prior Unit's narrower scope.**

### Why `ReasoningContext` must not cross this boundary

`ReasoningContext` (`src/interfaces/ReasoningProvider.kt`, line 34:
`data class ReasoningContext(val entries: List<String>)`) is assembled,
in production, by whatever `ReasoningContextAssembler` implementation is
registered — built from Memory/World Model/conversation-history sources —
for exactly one purpose: helping `ReasoningProvider.reason()` classify a
`Turn` into `Reply`/`Goal`/`NoAction`. Its own contract
(`ReasoningContextAssembler.kt`) states plainly that an implementation is
"stateless... side-effect free... assembles a projection only," owned
entirely by the Reasoning boundary, and is consumed exactly once, by
`ReasoningProvider.reason()`, before a `Goal` is even known to exist.

By the time `GoalPlanningHandoffCoordinator` receives a `Goal`, that
classification has already happened and `ReasoningContext` has already
served its purpose. Reusing the same assembled value for Candidate
Generation would not be reference-based context sharing — it would be
**copying one component's already-consumed internal artifact into a
second, conceptually distinct component**, exactly what AD-011 forbids
("never by copying another component's internal state"). It would also
conflate two things `PlannerRuntimeSpecification.md` Section 9 already,
explicitly, keeps separate: Reasoning Context (Reasoning's own,
classification-scoped) and **Planning Context** (the Planner Runtime's
own, reference-based, gathered during `CONTEXT_GATHERING`, "not long-term
Memory," "not the World Model," "not Task Context, and not Agent
Context"). These are not the same store wearing two names; they are two
different stores with two different owners and two different purposes,
and this repository has already decided that on the record, independent
of anything this Unit adds.

### Why this is not merely "no ReasoningContext today, pending a fix"

A future, richer Candidate Generation input is not foreclosed by this
determination — it is correctly *redirected*. If Candidate Generation
ever legitimately needs conversation-, Memory-, or World-Model-derived
context, the correct future vehicle is a genuine, independently-assembled
**Planning Context** — analogous in *kind* to `ReasoningContext` (a
bounded, already-assembled projection) but distinct in *identity and
ownership* (assembled for Planning's own purposes, by a Planning-owned
assembler, never by reusing Reasoning's). Designing that assembler is
explicitly deferred (Section 9) — not because it is unimportant, but
because it is a separate, larger architectural decision (touching Memory
Source and World Model Source integration into planning for the first
time) than this Unit's charter, and forcing it into this Unit would
repeat the exact mistake `PLANNER_RUNTIME_CONTRACT_DESIGN.md`'s own "Why
this unit exists" section once had to correct for elsewhere in this
project: design work performed retroactively, under pressure of an
adjacent implementation, rather than chartered on its own terms.

### Disposition of the three options posed

- **"ReasoningContext should legitimately cross this boundary"** —
  rejected, for the reasons above.
- **"Another coordinator should own Candidate Generation"** — partially
  orthogonal to the `ReasoningContext` question and **not required** by
  this resolution: since `PlanCandidateGenerator`'s only legitimate input
  is `PlanningRequest` (Section 1), *any* coordinator capable of
  constructing or holding one — including `GoalPlanningHandoffCoordinator`
  itself, unmodified in its own information access — could structurally
  invoke it without needing `ReasoningContext` either way. **Which
  coordinator actually becomes the caller of
  `PlanCandidateGenerator.generate()` and, later, `PlannerRuntime.plan()`
  is deliberately left open by this Unit** (Section 9) — it is a
  production-wiring/composition placement question, not an information-
  boundary question, and resolving it would require either revising
  `GoalPlanningHandoffCoordinator` (excluded from this Unit) or wiring
  `PlannerRuntime` into production (excluded from this Unit). Importantly,
  this deferral is now low-risk: whichever coordinator is eventually
  chosen needs nothing more than a `PlanningRequest` and a
  `PlanCandidateGenerator` reference — the harder question (what context
  crosses which boundary) is already settled by this Section.
- **"GoalPlanningHandoffCoordinator should remain intentionally
  ignorant of ReasoningContext"** — **confirmed.** This is not a gap to
  close. It is the correct, permanent shape of this boundary.

## Section 4 — Public Contract

Designed only now that Sections 1–3 are settled. Deliberately minimal, in
direct proportion to how narrow Section 1's information boundary turned
out to be.

```kotlin
// Illustrative signature only -- not implemented by this document.
interface PlanCandidateGenerator {
    suspend fun generate(request: PlanningRequest): List<PlanCandidate>
}
```

**Input contract.** Exactly one parameter: `request: PlanningRequest`,
already non-blank on `goal` and `correlationId` by that type's own `init`
check. No other parameter — Section 1 settled that nothing else is
legitimately available. No default value, mirroring
`GoalPlanningHandoffCoordinator`'s own "no default, explicit at every call
site" precedent for its single dependency.

**Why `suspend`.** Identical reasoning to `PlanDecision.decide` and
`ReasoningProvider.reason`: nothing in a first, deterministic
implementation needs to suspend, but `PlannerRuntimeSpecification.md`
Section 14 and AD-010 (Model Independence) anticipate a future
model-backed, rule-based, or human-in-the-loop generator, any of which
would need to suspend (an HTTP call, a UI wait). Declaring `generate`
`suspend` now avoids a breaking interface change later — the same
forward-compatibility reasoning already applied twice in this codebase for
exactly this category of seam.

**Output contract.** `List<PlanCandidate>` — the exact type
`PlanDecision.decide` and `PlannerRuntime.plan()` already accept. No new
wrapper or sealed result type is introduced (Section 5 explains why:
there is no "decision" happening here, only production). An empty list is
a fully valid, non-exceptional return value (Section 6).

**Failure contract.** `generate` may throw for a genuine implementation-
level fault (timeout, crash, malformed upstream output) — propagated
unchanged, uncaught, exactly as `ReasoningProvider.reason()` and
`GoalPlanningHandoffCoordinator.initiatePlanning` already do, ultimately
surfacing via `ParkerRuntime.submitOwnerMessage`'s existing outer
`try`/`catch` as `ParkerRuntimeOutcome.Failed`. It must never throw merely
because it could not decompose the Goal — that is an empty list (Section
6), not a fault, mirroring `ReasoningProviderResponse.NoAction`'s own
documented discipline: "a confident semantic determination... must never
be used as a catch-all for... failures," applied here in reverse (an
empty list is the confident determination; a throw is reserved for
genuine faults only).

**Placement in the source tree.** A new file,
`src/contracts/PlanCandidateGenerator.kt` — not an addition to the
already-accepted, already-tested `src/contracts/PlanDecision.kt` — keeping
this Unit's own new type additive and isolated, the same minimal-blast-
radius pattern the Reasoning-to-Planning Handoff already used
(`GoalPlanningHandoffCoordinator.kt`, `ConversationOutcome.kt` were both
new files, not edits to existing ones).

## Section 5 — Output Model

**One candidate.** The ordinary default case — legitimate, requires no
special handling.

**Many candidates.** Legitimate, per `PlannerRuntimeSpecification.md`
Section 4 ("a Planning Session MAY generate one or many Plan Candidates").
No cap is defined by this contract; a future Planner Policy bound (max
candidate count) is Future Work (Section 9), not decided here.

**Zero candidates.** Legitimate, not an error, not an exception — see
Section 6.

### Ownership of ranking, ordering, confidence, and rationale

| Concern | Owner | Basis |
|---|---|---|
| **Ranking / selection authority** — deciding *which* candidate is chosen | `PlanDecision` / `PlannerRuntime` (unchanged, already implemented) | `PlanDecision.decide(goal, candidates): PlanDecisionResult`; `DefaultPlanDecision`'s four deterministic rules (duplicate ID, blank goal, goal mismatch, not-selected-in-generation-order). `PlanCandidateGenerator` has no visibility into, and no say over, this outcome. |
| **List order (generation order)** | `PlanCandidateGenerator` | The order in which candidates are returned is meaningful: `DefaultPlanDecision`'s own tie-break rule is "first valid, non-duplicate candidate **in generation order**." `PlanCandidateGenerator` determines that order as a byproduct of how it produces candidates — this is not a quality ranking, only a sequencing fact `PlanDecision` already relies on. |
| **Confidence** | `PlanCandidateGenerator`, optional, informal only | `PlannerRuntimeSpecification.md` Section 10: Confidence "MAY be included as a coarse, qualitative indicator if whatever produced the underlying Plan Candidate has one to offer... free to omit this field entirely." `PlanCandidate` has no dedicated `Confidence` field today (unlike `TaskProposal`) — a generator wishing to express confidence has only free-text `rationale` available. Formalising a `Confidence` field is Future Work (Section 9), not decided here. |
| **Rationale — the candidate's own** | `PlanCandidateGenerator`, optional, primary author | `PlanCandidate.rationale: String = ""` is an optional carry-forward field; a generator populates it to explain *why it proposed this decomposition*. |
| **Rationale — the selection's own** | `PlannerRuntime` / `DefaultPlanDecision`, unchanged, already implemented | `InMemoryPlannerRuntime.buildProposal` already supplies a fallback rationale — "Selected Plan Candidate '...' via DefaultPlanDecision... first valid, non-duplicate candidate in generation order" — **only when the winning candidate's own `rationale` is blank**. This is a distinct, already-implemented second layer explaining *why this candidate over the others*, not *why this decomposition at all*. This Unit changes nothing about it. |

## Section 6 — Failure Semantics

Each category addressed as an architectural boundary statement only — no
new outcome type, no `PlannerRuntime` redesign, nothing implemented.

**Ambiguous goal.** Not distinctly representable by `List<PlanCandidate>`
today. `PlanCandidateGenerator` has exactly two honest options: produce
its best-effort interpretation(s) as one or more candidates, recording the
ambiguity as an explicit Assumption in `rationale`/`constraints`
(mirroring `PlannerRuntimeSpecification.md` Section 4's "Assumption"
concept and Section 12's identical treatment of "Permission uncertainty" —
"recorded... as an explicit Assumption... rather than silently guessed at
or omitted"); or return an empty list if no interpretation is confident
enough to propose at all. No distinct signal exists, and none is invented
here — `WAITING_FOR_INPUT` remains unreachable (Section 9).

**Insufficient information.** Identical treatment to ambiguous goal, same
two honest options, same absence of a distinct signal.

**Impossible request.** The Goal cannot be decomposed into any coherent
`PlanCandidate` under any interpretation → an empty list. This is, by
design, indistinguishable at the interface level from "no candidate
available" below — inventing a distinction would require a new return
type this Contract Design deliberately does not introduce.

**Unsafe request.** `PlanCandidateGenerator` has no authority to refuse,
block, or veto a Goal (Section 7 — it never authorises). Its only lawful
choices are: propose a candidate labelled with elevated
`riskEstimate`/`anticipatedPermissionActions`/`constraints`, deferring
real evaluation to the unchanged, downstream Permission Engine at actual
`ExecutionRequest` time; or return an empty list — honestly
indistinguishable, today, from "impossible request." The
safety-refusal/incapacity distinction named as unresolved in the
Governance Review is restated here, not solved.

**No candidate available.** Return an empty `List<PlanCandidate>` — not an
exception, not a sentinel value. `PlannerRuntime.plan()` already handles
this deterministically and correctly today: `PlanDecisionResult.NoViableCandidate`
→ `PlanningSessionResult.Failed`, reason "no Plan Candidates were supplied
for this Planning Session." No revision to `PlannerRuntime` is required or
proposed.

## Section 7 — Trust Boundary

**Not revisited — confirmed exactly as settled by the Governance Review
(Section 10 there), restated for completeness only:**

- **Proposes only.** `PlanCandidateGenerator`'s sole output is
  `List<PlanCandidate>` — never a `TaskProposal`, never a Task, never an
  `ExecutionRequest`.
- **Never authorises.** No type it produces or consumes is a
  `PermissionDecision`.
- **Never executes.** No invocable `Tool` reference, ever (ADR-001,
  AD-003).
- **Never schedules.** No path from `PlanCandidate` to any `Task`/
  `TaskStatus` field except by first becoming a selected candidate, then a
  `TaskProposal`, then an accepted Task — each a separate component's own
  decision, none this component's.
- **Never creates tasks.** Restated from `PLANNER_RUNTIME_CONTRACT_DESIGN.md`'s
  own Constitutional Boundary, binding transitively.
- **Never invokes tools.** Identical to "never executes."
- **Never bypasses permissions.** `anticipatedPermissionActions`/
  `requiredCapabilities`/`riskEstimate` remain advisory labelling only,
  exactly as `PlannerRuntimeSpecification.md` Section 8 already requires
  of `TaskProposal`'s equivalent fields.

## Section 8 — Existing Contracts

**No contract revision is genuinely required. This Contract Design is
purely additive.**

- **`PlanCandidate`** — No revision required. Its already-approved,
  two-tier field shape (required: `planCandidateId`, `goal`; optional
  carry-forward: `rationale`, `riskEstimate`, `requiredCapabilities`,
  `anticipatedPermissionActions`, `constraints`, `dependencies`,
  `contextReferences`, `resourceReferences`, `expectedOutputs`) is
  sufficient as the output type for a real generator, exactly as it
  already is for the test-only `DeterministicPlannerHarness.kt`. The
  disclosed `Confidence`-field gap (Governance Review Section 6) remains a
  possible future addition, not a required one — deferred (Section 9).
- **`PlanDecision`** — No revision required. `decide(goal, candidates):
  PlanDecisionResult` already consumes exactly the `List<PlanCandidate>`
  shape `PlanCandidateGenerator.generate` would produce.
- **`PlanningRequest`** — No revision required. This Contract Design's own
  decision to use it, unmodified, as `PlanCandidateGenerator`'s sole input
  (Section 1) is itself confirmation that its existing field set is
  sufficient; no field needs to be added, removed, or changed.
- **`PlannerRuntime`** — No revision required. `plan(request, candidates)`'s
  signature already accepts an externally-produced `List<PlanCandidate>`;
  a real `PlanCandidateGenerator` implementation slots in ahead of a
  `plan()` call without any interface change.
- **`GoalPlanningHandoffCoordinator`** — No revision required, and none
  proposed, consistent with this Unit's explicit exclusion. Section 3's
  resolution confirms this is not merely permitted by the exclusion but
  independently correct: nothing about this Unit's information boundary
  or ownership determination requires `GoalPlanningHandoffCoordinator` to
  change.

## Section 9 — Future Work (deliberately deferred, not solved)

- **Placement of invocation.** Which coordinator ultimately holds a
  `PlanCandidateGenerator` reference and calls
  `PlannerRuntime.plan()` — a revised `GoalPlanningHandoffCoordinator`, or
  a new, separate coordinator. Deliberately left open (Section 3); requires
  either revising `GoalPlanningHandoffCoordinator` or wiring `PlannerRuntime`
  into production, both excluded from this Unit.
- **`WAITING_FOR_INPUT` reachability.** Ambiguous-goal and
  insufficient-information handling have no contractual channel toward
  this already-specified, still entirely unreached lifecycle state
  (Section 6).
- **Safety-refusal distinction.** No field or signal distinguishes "I
  decline to propose this for safety reasons" from "I could not form any
  candidate at all" (Section 6).
- **Cross-goal conflict.** Conflicting Goals across Planning Sessions, or
  against a future persistent Goal Manager (Chapter 23), remain entirely
  unaddressed; resolving this would touch Chapter 23, explicitly excluded.
- **Confidence modelling.** Whether `PlanCandidate` should gain a formal,
  optional `Confidence` field to match `TaskProposal`'s already-approved
  one (Section 5).
- **Multi-goal reasoning.** How, or whether, a single Candidate Generation
  attempt should ever consider more than one Goal at a time — not raised
  by any existing contract and not addressed here.
- **A genuine, independently-owned Planning Context assembler.** Distinct
  from `ReasoningContextAssembler`, reference-based, Memory-/World-Model-
  /conversation-aware, assembled for Planning's own purposes — the correct
  future vehicle if Candidate Generation is ever found to need richer
  context than `PlanningRequest` alone provides (Section 3). Not designed
  here.
- **Planner Policy.** A bounded-configuration concept
  (`PlannerRuntimeSpecification.md` Section 4) — e.g. a maximum candidate
  count or generation-duration bound — named in the specification but
  never given a contract shape anywhere in `src/`.

## Recommendation

**Ready for Scope Lock.**

Every section this Unit was chartered to complete reached a definite,
justified conclusion, not a deferred one: the information boundary
(Section 1) is fully classified, item by item; ownership (Section 2) is
confirmed as a dedicated `PlanCandidateGenerator`, distinct from
`PlannerRuntime` and from `GoalPlanningHandoffCoordinator` as currently
scoped; the central placement tension (Section 3) — whether
`ReasoningContext` crosses the `GoalPlanningHandoffCoordinator` boundary —
is resolved explicitly and permanently, not left open; the public contract
(Section 4) is a single, minimal, `suspend` method consuming and producing
only already-approved types; the output model (Section 5) and failure
semantics (Section 6) are fully specified within the existing contract
surface, inventing nothing; the trust boundary (Section 7) required no
new analysis, only confirmation; and no existing contract requires
revision (Section 8) — this design is purely additive.

The items in Section 9 are genuinely separable future questions, not
gaps in this Unit's own charter — each was already named, not newly
discovered, by the preceding Governance Review, and none blocks a Scope
Lock for the narrow, additive contract this document actually specifies:
one new interface, one new file, zero revisions to existing production
code.
