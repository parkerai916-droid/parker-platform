## Status

**Governance review only. No Kotlin, no interfaces, no contracts, no
tests, no dependency or build changes exist anywhere in this document or
arise from it.** Nothing under `src/` or `tests/` is touched. This
document does not begin Contract Design and does not produce a Scope
Lock — it determines whether Contract Design may begin, and on what
terms.

**Repository position.** Branch `main`. Latest verified implementation
includes the Reasoning-to-Planning Handoff (`GoalPlanningHandoffCoordinator`,
`ConversationOutcome`, `ParkerRuntimeOutcome.PlanningDeferred`), commit

### Findings not previously recorded this precisely

**Finding 1 — ownership of candidate generation is already settled in the
negative, twice over, by already-accepted documents.** Both
`PlannerRuntimeSpecification.md` (Section 2, Section 3 Non-Goals, Section
14) and `PLANNER_RUNTIME_CONTRACT_DESIGN.md` (Type 2's ownership note, the
`PlanningRequest` correction removing `candidates` from the request
specifically to keep them externally supplied) already rule out
`PlannerRuntime` as the owner. `InMemoryPlannerRuntime`'s own KDoc restates
this a third time, as implemented fact, not aspiration. This is not a new
determination this review is making — it is a confirmation of an existing,
multiply-redundant architectural position.

**Finding 2 — there is no existing interface for "the thing that produces
candidates."** `ReasoningProvider` and `PlanDecision` are both real,
`suspend`, pluggable, model-independent interfaces with exactly this
shape of responsibility for their own respective boundaries (classifying a
Turn; choosing among supplied candidates). No analogous interface exists
anywhere in `src/contracts` or `src/interfaces` for generating candidates
in between them. This is the actual gap this review exists to characterise.

**Finding 3 — a real, disclosed tension exists between this review's
likely ownership recommendation and `GoalPlanningHandoffCoordinator`'s own
forward-looking KDoc.** That KDoc's own words describe a future Unit that
"replaces `[initiatePlanning]`'s body with a real `plan()` call" —
phrasing that reads as if `GoalPlanningHandoffCoordinator` itself grows a
`PlannerRuntime` dependency and, by implication, whatever candidate
generation feeds it. This review's own analysis (Section 3) favours a
separate, dedicated component instead, for single-responsibility reasons
consistent with this codebase's coordinator pattern. Both are structurally
legitimate; this tension is surfaced explicitly in Section 12, not
silently resolved either way.

**Finding 4 — the current handoff boundary does not carry enough
information for a real candidate generator to consult Memory, World
Model, or conversation history, even if one existed today.**
`GoalPlanningHandoffCoordinator.initiatePlanning`'s own signature carries
only `InboundOwnerMessage` and `Goal` — not the `ReasoningContext` already
assembled one step earlier in the same request's lifecycle. This is a
direct, disclosed consequence of the Reasoning-to-Planning Handoff's own
deliberately narrow Scope Lock, not a defect in that Unit — but it is a
concrete constraint the next Contract Design must address if candidate
generation is expected to be context-informed at all.

**Finding 5 — the "zero candidates" failure path needs no new contract.**
`InMemoryPlannerRuntime.plan` already handles an empty `candidates` list
correctly and truthfully today: `PlanningSessionResult.Failed` via
`PlanDecisionResult.NoViableCandidate`, reason "no Plan Candidates were
supplied for this Planning Session." A future candidate generator that
legitimately cannot decompose a Goal needs only to return an empty list —
no new `PipelineStage`, exception type, or outcome variant is required for
this specific case.

## 2. The Question, Stated Precisely

`PlannerRuntime.plan(request: PlanningRequest, candidates: List<PlanCandidate>)`
already exists, is implemented, and is tested. `GoalPlanningHandoffCoordinator`
already exists and already constructs a well-formed `PlanningRequest` from
a `Goal`. Nothing in this repository constructs a `PlanCandidate` outside
of test fixtures (`DeterministicPlannerHarness.kt`, `tests/`). The
question is not whether candidate generation belongs somewhere upstream of
`PlannerRuntime.plan()` — every existing document already agrees it does
— but precisely which component that should be, what it is and is not
responsible for, what it may legitimately read, what it must produce, and
where its honest failure and safety boundaries lie.

## 3. Ownership (Question 1)

### 3.1 Should `PlannerRuntime` own it?

**No.** Settled, not merely recommended, by three independent
already-accepted sources: `PlannerRuntimeSpecification.md` Section 3
Non-Goals does not list candidate generation as in-scope and Section 2's
"Model independence" design goal requires the Planner Runtime's own
behaviour to be "deterministic given the same Planning Context, Plan
Candidates, and Task Manager/Permission Engine state, regardless of what
— or whether a model — sits upstream of Plan Candidate generation";
`PLANNER_RUNTIME_CONTRACT_DESIGN.md` Type 6 deliberately removed
`candidates` from `PlanningRequest` specifically so they would be supplied
externally to `plan()`, not generated inside it; `InMemoryPlannerRuntime`'s
own KDoc states "Candidate generation is not this class's job." Reopening
this would mean reversing an already-implemented, already-tested contract
decision for no motivating new requirement.

### 3.2 Should `GoalPlanningHandoffCoordinator` own it?

**Not as currently scoped, though its own KDoc leaves the door open
(Finding 3).** `GoalPlanningHandoffCoordinator` today is a pure sequencing
coordinator — its entire documented justification for existing at all
rests on having exactly one constructor dependency
(`planningSessionIdFactory: () -> String`), which its own KDoc calls "the
structural guarantee" of what it cannot reach. Every other coordinator in
this codebase (`ConversationTurnReasoningCoordinator`,
`CommunicationConversationCoordinator`, `ReplyDeliveryCoordinator`,
`ConversationReplyCoordinator`) follows the identical convention: one
narrow responsibility, a minimal dependency list that is itself the proof
of scope. Folding substantive candidate generation into this same class
would collapse two distinct responsibilities — sequencing a handoff, and
producing the actual proposed content of a plan — into one class, breaking
that convention for the first time in this codebase's history, not
extending it.

### 3.3 Should a dedicated Candidate Generator own it?

**Yes — recommended.** A new, narrowly-scoped, pluggable interface,
analogous in kind to `ReasoningProvider` and `PlanDecision`: both are
`suspend`, single-method, explicitly model-independent seams that this
codebase already trusts with exactly this category of responsibility
(interpreting input and producing a structured judgment, without holding
executable authority). Candidate generation is architecturally the same
*kind* of thing — interpreting a Goal (plus whatever context it
legitimately receives, Section 5) and producing structured proposals —
not a deterministic sequencing step. Placing it behind its own interface:

- preserves `GoalPlanningHandoffCoordinator`'s existing "one dependency,
  structural guarantee" convention, whether that class is later revised to
  hold this new dependency directly, or a different coordinator is
  introduced to hold it instead (Section 12 leaves this specific
  placement question open, deliberately, for Contract Design);
- matches AD-010 (Model Independence) exactly: "Plan Candidate generation
  ... [is an] explicitly swappable implementation detail" — a concrete
  interface is what makes something actually swappable, rather than
  swappable only in principle;
- requires no revision to `PlannerRuntime.plan()`'s already-accepted
  signature, since candidates would still arrive as an externally-produced
  `List<PlanCandidate>`, exactly as that signature already expects.

### 3.4 Should some other runtime component own it?

No other existing runtime component (`TaskManagerRuntime`, `AgentRuntime`,
`ExecutionPipeline`, `PermissionEngine`, `ConversationEngine`) has any
documented relationship to Plan Candidates at all; none is considered a
serious candidate and none is analysed further here.

## 4. Responsibilities (Question 2)

Candidate generation is responsible for exactly one thing: given a Goal
(and whatever legitimately-available context, Section 5), producing zero,
one, or more structurally well-formed `PlanCandidate` values — proposed
decompositions of how that Goal might be pursued. Nothing more.

**Distinguished from reasoning.** `ReasoningProvider`'s job is prior in
time and different in kind: it decides *whether* a Turn expresses
something to reply to, act on, or ignore (`Reply`/`Goal`/`NoAction`).
Candidate generation begins only after that classification has already
concluded "this is a Goal" — it does not re-decide whether to act at all,
it decomposes an already-accepted Goal into concrete approaches.

**Distinguished from planning.** "Planning," in this repository's own
vocabulary, is the `PlannerRuntime`'s full Planning Session lifecycle:
`CREATED → CONTEXT_GATHERING → ANALYSING → PROPOSING → SUBMITTED →
{COMPLETED, REJECTED}`. Candidate generation supplies raw material
consumed *during* `ANALYSING`; it does not gather Planning Context itself
(that is `CONTEXT_GATHERING`, a `PlannerRuntime`-owned step per
`PlannerRuntimeSpecification.md` Section 5), does not select among
candidates (`PlanDecision`'s job, Section 6 below), and does not construct
or submit a `TaskProposal` (`PROPOSING`/`SUBMITTED`, also
`PlannerRuntime`-owned).

**Distinguished from task management.** `TaskManagerRuntime` decides
whether an already-submitted `TaskProposal` becomes a real Task
(`TaskProposalIntake.submitProposal`). Candidate generation never
constructs or touches a `TaskProposal` or a `Task` at all — its output
stops at `PlanCandidate`, one full layer upstream of a Task Proposal.

**Distinguished from execution.** Candidate generation holds no invocable
`Tool` reference, no `ExecutionRequest`, and causes no external effect —
restating ADR-001 ("Models Never Execute Tools") and AD-003 for this
layer specifically. Every field a `PlanCandidate` carries that resembles
an eventual capability or permission need (`requiredCapabilities`,
`anticipatedPermissionActions`) is advisory labelling only, identical in
kind and force to the same restriction `PlannerRuntimeSpecification.md`
Section 8 already places on `TaskProposal`'s own equivalent fields.

## 5. Inputs (Question 3)

What is legitimately available to candidate generation, per existing,
already-accepted contracts:

- **Goal text.** `ReasoningProviderResponse.Goal.text` /
  `PlanningRequest.goal` — the primary, always-available input.
- **Conversation.** `InboundOwnerMessage` (sender, correlation, timestamp)
  is already available at the point `GoalPlanningHandoffCoordinator`
  constructs a `PlanningRequest`. Fuller conversation history is not
  currently threaded this far: `ReasoningContext` (which is built, in
  production, from conversation-history/Memory/World-Model sources) stops
  at `ReasoningProvider.reason()` today (Finding 4). Whether, and how, a
  candidate generator should receive conversation history at all is a
  Contract Design question, not decided here.
- **Memory / World Model.** Legitimately available only by reference,
  never by direct read or write, per `PlannerRuntimeSpecification.md`
  Section 9 ("Planning Context... may later reference Memory or World
  Model entries, but does not implement them") and Section 3's Non-Goals
  ("Memory implementation... untouched," "World Model implementation...
  untouched"). Per AD-011 (Context Is Reference-Based), the same
  reference-only discipline that governs `PlannerRuntime`'s own Planning
  Context would govern candidate generation's access to either, if and
  when either is wired at all — today, neither is wired into this
  boundary in any form (Finding 4).
- **Authenticated Principal.** `initiatingPrincipalId`
  (`InboundOwnerMessage.senderPrincipalId`) is already threaded through
  `PlanningRequest`. Identity *resolution* (existence-check only, per
  `IMPLEMENTATION_GAPS.md` #37) happens inside `PlannerRuntime.plan()`,
  not before or during candidate generation — a generator may read the
  identifier for labelling purposes but performs no resolution or status
  check of its own.
- **Permissions already known.** Candidate generation may only label
  anticipated permission implications (`anticipatedPermissionActions`,
  `requiredCapabilities`), never evaluate or grant them —
  `PlannerRuntimeSpecification.md` Section 8's "advisory labelling, not a
  `PermissionDecision`" rule applies with identical force here, one layer
  further from authority than where that rule was originally written.
- **Runtime context.** Whatever a future Planning Context implementation
  makes available by reference (Resource references via the read-only
  Resource Registry, Task references, Agent Run references, event-history
  references, available-capability references via read-only Tool
  Registry/Agent Runtime discovery) — per `PlannerRuntimeSpecification.md`
  Section 9, none of it copied inline, none of it invocable.

## 6. Outputs (Question 4)

A production `PlanCandidate` is exactly the type already approved by
`PLANNER_RUNTIME_CONTRACT_DESIGN.md` Type 2 and implemented in
`src/contracts/PlanDecision.kt` (lines 76–88). No revision to this type's
own field shape is identified as necessary by this review, with one
disclosed exception (Confidence, below).

**Required.** `planCandidateId: PlanCandidateId` (uniqueness enforced by
`PlanDecision`, not by construction); `goal: String` (deliberately
**not** validated at construction — a candidate generator may legitimately
produce a blank or mismatched `goal`, and recognising that as invalid
remains `PlanDecision`'s job, not something the type itself forbids,
"since forbidding it would make the rejection path untestable").

**Optional carry-forward** (identical name/type/default to the
corresponding `TaskProposal` field — reused, not new schema):
`rationale`, `riskEstimate`, `requiredCapabilities`,
`anticipatedPermissionActions`, `constraints`, `dependencies`,
`contextReferences`, `resourceReferences`, `expectedOutputs`. A candidate
generator is free to omit every one of these; `PlanDecision`'s own logic
reads only `planCandidateId`/`goal`.

**Deliberately does not contain:**

- No permission decision, and no field that could be mistaken for one.
- No execution reference of any kind (no `Tool`, no `ExecutionRequest`).
- No Task or `TaskProposal` identity — a `PlanCandidate` that is never
  selected never becomes a `TaskProposal` at all.
- No mandatory confidence/probability score — consistent with
  `PlannerRuntimeSpecification.md` Section 10's explicit refusal to
  "mandate any particular confidence representation or scale."
- **Disclosed gap:** `TaskProposal` already has an approved, optional
  `Confidence` field (Section 10); `PlanCandidate` does not. A real
  generator wanting to express uncertainty about a specific candidate has
  no typed field for it today, only free-text `rationale`. Named here as
  a possible future field addition, not designed or decided.

## 7. Multiple Candidates (Question 5)

**Parker should not always produce exactly one.** This is already the
specified and implemented behaviour, not a new decision:
`PlannerRuntimeSpecification.md` Section 4 states plainly "a Planning
Session MAY generate one or many Plan Candidates," and
`InMemoryPlannerRuntime.plan` already, correctly, handles zero (empty
list → `NoViableCandidate` → `Failed`), one, or many (iterated,
published as `planner.candidate_generated` events, evaluated by
`DefaultPlanDecision`'s four deterministic rules) without any change
required. Forcing a future generator to always produce exactly one would
be a new, artificial constraint this review does not recommend inventing —
it would also erase the legitimate "I cannot decompose this Goal at all"
outcome (Section 9) by conflating it with "I decomposed it one way."

**Under what conditions.** Not decided by this review — that belongs to
the eventual Candidate Generator's own Contract Design — but architecturally:
zero is legitimate when a Goal cannot be meaningfully decomposed at all;
one is the ordinary default case; many is legitimate when genuinely
distinct strategies exist for pursuing the same Goal. This review notes
one distinction worth preserving in that future design: "generation
produced zero candidates" (an honest admission by the generator) is a
different event from "generation produced N candidates, all rejected by
`PlanDecision`" (an evaluation outcome) — both already resolve to the same
`PlanningSessionResult.Failed` today, and this review does not recommend
changing that, only notes the distinction exists at the generation layer
even though it collapses one layer downstream.

## 8. Deliberation (Question 6)

**Candidate generation does not perform deliberation.** Chapter 20's own
six lines are unambiguous: "The Planner constructs candidate execution
plans. The Deliberation Service compares them... Planning explores.
Deliberation evaluates." Candidate generation is entirely on the
"explores" side. Comparing, ranking, selecting, or rejecting candidates is
`PlanDecision`'s job exclusively — already implemented
(`DefaultPlanDecision`'s four deterministic rules: duplicate ID, blank
goal, goal mismatch, not-selected-in-generation-order) and already
consumed inside `InMemoryPlannerRuntime.plan`.

**Generation vs. selection, stated as a clean boundary:**

- **Generation** produces the `List<PlanCandidate>` argument to
  `PlannerRuntime.plan()`. It happens entirely before that call — outside
  `PlannerRuntime`'s own lifecycle — and has no visibility into, and no
  say over, which candidate is ultimately chosen.
- **Selection** is `PlanDecision.decide(goal, candidates) →
  PlanDecisionResult`, consumed inside `plan()`'s own `ANALYSING` step.
  It never generates a candidate of its own; it only evaluates what it is
  given.

**Whether Chapter 20's "Deliberation Service" is the same thing as
`PlanDecision`, or a distinct future component, remains an open question
— recorded, not resolved, by `PlannerRuntimeSpecification.md` Section 1
itself, and not resolved by this review either.** This review's own
scope does not require settling it: regardless of the answer, candidate
generation is not that component, under either reading.

## 9. Failure Semantics (Question 7)

Each of the five requested categories, without inventing implementation:

**No candidate possible.** Already fully specified and implemented
(Finding 5, Section 7 above). A generator legitimately returns an empty
list; `PlannerRuntime.plan()` already reports this truthfully as
`PlanningSessionResult.Failed`, reason "no Plan Candidates were supplied
for this Planning Session." No new contract is required for this specific
case.

**Ambiguous goal.** `PlannerRuntimeSpecification.md` Section 5 reserves
`WAITING_FOR_INPUT` for exactly this situation ("paused pending an input
it cannot supply itself... a clarification only a human or another system
can provide"), reachable in the specification from `CONTEXT_GATHERING`,
`ANALYSING`, or `PROPOSING`. `InMemoryPlannerRuntime` does not reach this
state today — `PLANNER_RUNTIME_CONTRACT_DESIGN.md` Type 8/9 records this
as "a documented coverage gap, not an invented restriction," since "no
Planner reasoning [exists] to detect insufficient context." **There is
today no contractual channel by which a candidate generator could signal
ambiguity back toward `WAITING_FOR_INPUT` at all** — this is a genuine,
disclosed contract insufficiency (Section 11), not something this review
invents a resolution for.

**Insufficient information.** The identical gap as ambiguous goal, by the
same specification section ("Insufficient context... transitions to
`WAITING_FOR_INPUT`... if the missing context remains unavailable...
transitions to `FAILED`"). Without a real channel to `WAITING_FOR_INPUT`,
a generator facing insufficient information today has only two honest
options: return no candidate (indistinguishable, at the `PlannerRuntime`
level, from "cannot decompose at all") or return a candidate whose
`rationale`/risk notes record the missing information as an explicit
Assumption, per Section 12's own "Permission uncertainty" treatment
extended by analogy. Neither is a defect in this review's own
recommendation — both are already-available, honest choices under the
existing contract — but the sharper, dedicated signal `WAITING_FOR_INPUT`
implies does not exist end-to-end yet.

**Unsafe goal.** Candidate generation has no authority to declare a Goal
categorically disallowed — that determination belongs to the Permission
Engine, downstream, at real `ExecutionRequest` time
(`AUTHENTICATION_AND_TRUST_GOVERNANCE.md`'s "Reasoning cannot grant
permissions"; `PlannerRuntimeSpecification.md` Section 8's
advisory-labelling-only rule, restated in Section 10 above). The only
lawful channel today for surfacing risk is the existing advisory
`riskEstimate`/`anticipatedPermissionActions`/`constraints` fields already
on `PlanCandidate`. **A real, disclosed gap:** nothing in `PlanCandidate`'s
current shape distinguishes "I propose this, but flag it as high-risk"
from "I decline to propose anything for this Goal because it appears
unsafe" — both would currently present identically as either a
risk-labelled candidate or an empty list, with no field or enum
expressing the second case as a deliberate refusal rather than an honest
incapacity. Naming this distinction is this review's contribution;
resolving it is not.

**Conflicting goals.** `PlannerRuntimeSpecification.md` Section 12 defines
*conflicting constraints* within one Planning Session as a `FAILED`
outcome — it does not define conflicting *goals* as a concept at all.
`PlanningRequest` carries exactly one `goal: String`; there is no existing
notion of two Goals in tension within a single Planning Session, and no
existing notion of a new Goal conflicting with an already-in-flight
Planning Session or with a persistent objective tracked elsewhere. The
latter would necessarily touch Chapter 23's Goal Manager — explicitly
excluded from this review — so this category is recorded as unresolved
and out of this review's reach, not answered by omission.

## 10. Trust Boundary (Question 8)

**Confirmed: candidate generation proposes only.** Every existing
restriction placed on `PlannerRuntime` itself — which is already one full
layer closer to authority than candidate generation would be — applies
with at least equal force here, by direct extension of already-accepted
governance:

- **Never authorises.** AD-002 (Proposal Before Authority); no existing
  type anywhere in the planning-related contract set produces a
  `PermissionDecision`, and none would be introduced for this boundary.
- **Never executes.** ADR-001 (Models Never Execute Tools), AD-003
  (Execution Pipeline Is the Sole Execution Authority);
  `PlannerRuntimeSpecification.md` Section 13 ("No direct tool execution")
  — candidate generation holds no invocable `Tool` reference, one layer
  further removed than `PlannerRuntime` itself already is.
- **Never schedules.** No candidate-generation output writes any Task
  Manager Task field, directly or indirectly — `PlanCandidate` has no
  path to `Task`/`TaskStatus` except by first becoming a selected
  candidate, then a `TaskProposal`, then an accepted Task, each a separate
  component's own decision.
- **Never performs tools.** Restated identically from "never executes";
  `PlannerRuntimeSpecification.md` Section 3's Non-Goals apply
  transitively.
- **Never creates tasks.** `PLANNER_RUNTIME_CONTRACT_DESIGN.md`'s own
  Constitutional Boundary ("Planner must not create tasks directly")
  binds `PlannerRuntime`; a component upstream of `PlannerRuntime` has, by
  construction, no greater authority than the component it feeds.

No new authorisation, execution, scheduling, or task-creation capability
is introduced, implied, or required by anything in this review.

## 11. Existing Contracts — Sufficiency Review (Question 9)

**Sufficient, no revision identified as necessary:**

- `PlanCandidate`/`PlanCandidateId` field shape (required + optional
  carry-forward) — already well-specified, already constructible and
  consumable (`DeterministicPlannerHarness.kt` proves this today, for a
  test fixture).
- `PlanDecision`/`PlanDecisionResult`/`PlanRejection`/`PlanRejectionReason`
  — already correctly separates selection from generation (Section 8);
  no change needed merely to attach a real generator upstream.
- `PlannerRuntime.plan(request, candidates)`'s signature — already
  accepts an externally-supplied `List<PlanCandidate>`, a deliberate,
  already-accepted design correction specifically made to support this
  future attachment point.

**Insufficient, revision likely necessary (not designed here):**

- **No interface exists for candidate generation itself** (Finding 2) —
  the central gap this review characterises. Whatever Contract Design
  eventually names it, some new `src/contracts` or `src/interfaces` type
  is required; none exists to revise, only to add.
- **`GoalPlanningHandoffCoordinator`'s signature does not carry
  `ReasoningContext` or any Planning-Context-shaped input** (Finding 4).
  If a candidate generator is expected to be context-informed at all,
  either this coordinator's signature or the interception point itself
  needs revision — a small, disclosed, likely necessary change, not
  designed here.
- **No contractual channel exists for ambiguous-goal or
  insufficient-information signalling** (Section 9) — `WAITING_FOR_INPUT`
  is specified but has no implementation path and no signal a generator
  could produce today to reach it.
- **No field distinguishes a deliberate safety-motivated refusal from an
  honest incapacity to propose anything** (Section 9) — `PlanCandidate`'s
  current shape cannot express the difference.
- **`PlanCandidate` has no `Confidence` field**, unlike `TaskProposal`
  (Section 6) — a possible, undesigned future addition.

**Open, not itself a defect:** whether Chapter 20's Deliberation Service
is distinct from `PlanDecision` (Section 8) remains an open question this
review does not resolve, inherited unchanged from
`PlannerRuntimeSpecification.md`'s own Open Questions list.

## 12. Existing Implementation Constraints (Question 10)

- **`PlannerRuntime.plan()`'s signature is fixed and already
  externally-suppliable** — no implementation constraint blocks attaching
  a real generator without changing this interface.
- **`InMemoryPlannerRuntime`'s identity-resolution gate runs before
  candidates are consulted at all** (existence-check only, per gap #37,
  unresolved and unrelated to this review) — a real generator's own output
  only matters after that gate already passed; this is an existing,
  disclosed characteristic, not something this review changes or must
  route around.
- **`GoalPlanningHandoffCoordinator`'s own KDoc creates a real, disclosed
  tension with this review's ownership recommendation** (Finding 3): its
  own words anticipate a future revision that "replaces
  `[initiatePlanning]`'s body with a real `plan()` call," which reads most
  naturally as this same class growing both a candidate-generation-shaped
  dependency and a `PlannerRuntime` dependency directly. This review
  instead recommends (Section 3.3) that candidate generation live behind
  its own interface, consumed by whichever coordinator ultimately calls
  `plan()` — which may or may not be a revised
  `GoalPlanningHandoffCoordinator` itself. **This review does not decide
  which; it names the tension so Contract Design resolves it deliberately
  rather than by default.**
- **`ConversationOutcome.PlanningDeferred` and
  `ParkerRuntimeOutcome.PlanningDeferred` are both shaped narrowly around
  `GoalPlanningHandoffOutcome.Deferred`**, a single sealed variant today.
  `GoalPlanningHandoffCoordinator`'s own KDoc already anticipates this: "A
  future `Submitted`-shaped variant... is a distinct, separately-governed
  addition." Once real candidate generation and a real `plan()` call
  exist, this sealed type will need a new variant carrying a real
  `PlanningSessionResult`. This is a confirmed, already-disclosed
  downstream consequence of a future implementation Unit, restated here
  for completeness, not a new decision.
- **`ParkerRuntime.kt`'s composition root constructs no `PlannerRuntime`
  or `TaskManagerRuntime` instance today** — confirmed unchanged. Wiring
  either remains its own, separately-chartered unit, explicitly excluded
  from this review by the user's own instructions.

## 13. Architectural Options Considered

**Option A — Candidate generation lives inside `PlannerRuntime` (e.g.
`InMemoryPlannerRuntime` gains a generation step; `plan()` no longer takes
`candidates`).** Rejected. Directly contradicts `PlannerRuntimeSpecification.md`
Section 2/Section 3, AD-010, and the already-implemented, already-accepted
correction that specifically moved `candidates` out of `PlanningRequest`
and into `plan()`'s own external parameter for this exact reason.
Reopening this reverses settled architecture for no motivating
requirement.

**Option B — Candidate generation lives inside
`GoalPlanningHandoffCoordinator` itself, which also grows a `PlannerRuntime`
dependency and calls `plan()` directly.** Matches that class's own
forward-looking KDoc most literally (Finding 3). Rejected as the
recommended option, though not unreasonable: it collapses two distinct
responsibilities (sequencing a handoff; producing substantive plan
content) into one class, breaking the "one dependency, one structural
guarantee" convention every other coordinator in this codebase — including
this same class today — currently follows without exception.

**Option C — A new, dedicated, pluggable Candidate Generator interface,
analogous to `ReasoningProvider`/`PlanDecision`, consumed by whichever
component ultimately calls `PlannerRuntime.plan()`.** Recommended
(Section 3.3). Preserves the existing coordinator-pattern convention,
matches Model Independence concretely rather than only in principle, and
requires no revision to `PlannerRuntime.plan()`'s already-accepted
signature. Leaves open, deliberately, whether the component holding this
new dependency is a revised `GoalPlanningHandoffCoordinator` or a new
coordinator inserted between it and `PlannerRuntime` — a decision this
review defers to Contract Design (Section 12).

---

## 14. Recommended Ownership

**A dedicated, pluggable Candidate Generator component — not
`GoalPlanningHandoffCoordinator`, not `PlannerRuntime`, and no other
existing runtime component.** It sits architecturally between
`GoalPlanningHandoffCoordinator`'s existing `PlanningRequest` construction
and `PlannerRuntime.plan()`'s existing `candidates` parameter. Its exact
interface shape, its exact placement (inside a revised
`GoalPlanningHandoffCoordinator` or a new intermediate coordinator), and
its exact input signature are Contract Design questions, not settled
here — this review settles only that it should exist as a distinct,
named, swappable seam, and that it should not be folded into either of
the two components already forbidden, by already-accepted governance,
from owning it.

## 15. Risks and Dependencies

- **Hard dependency, restated from the Reasoning-to-Planning Handoff's own
  Finding 4, unchanged:** until a real Candidate Generator exists and is
  wired, every live `Goal` reaching `GoalPlanningHandoffCoordinator`
  remains correctly, honestly deferred (`GoalPlanningHandoffOutcome.Deferred`)
  — this review does not close that dependency, it characterises what
  closing it will eventually require.
- **`GoalPlanningHandoffCoordinator`'s own KDoc will need deliberate
  reconciliation, not silent reinterpretation, once Contract Design picks
  a placement** (Finding 3, Section 12).
- **`ReasoningContext` threading is a real, disclosed wiring gap**
  (Finding 4) that a context-informed generator design will need to
  resolve, likely via a small, disclosed revision to
  `GoalPlanningHandoffCoordinator`'s own signature or interception point.
- **`WAITING_FOR_INPUT` remains an unreached specification state** with no
  implementation path from any existing or newly-proposed component —
  ambiguous-goal and insufficient-information handling cannot be given a
  real contractual channel without a separately-chartered unit addressing
  this lifecycle gap directly.
- **The unsafe-goal / honest-incapacity distinction has no field to carry
  it** (Section 9) — a future `PlanCandidate` or generator-output revision
  may be needed, not designed here.
- **`ConversationOutcome`/`ParkerRuntimeOutcome`'s `PlanningDeferred`
  shape is single-variant today** and will need an additive revision once
  a real `plan()` call exists — already anticipated by the prior Unit's
  own KDoc, restated here as a concrete future dependency.
- **`PlannerRuntime`/`TaskManagerRuntime` remain unconstructed in
  `ParkerRuntime.kt`** — a separate, already-identified, already-excluded
  dependency this review does not attempt to close.

## 19. Readiness Determination — May Contract Design Proceed?

**Yes, narrowly — scoped to the ownership boundary this review actually
settles, not to the harder open questions it names but does not resolve.**

- **Ownership:** determined (Section 14) — a dedicated, pluggable
  Candidate Generator, not `PlannerRuntime`, not (as currently scoped)
  `GoalPlanningHandoffCoordinator`, and no other existing component.
- **Type-level sufficiency:** `PlanCandidate` and the rest of the existing
  Planner contract set need no revision merely to attach a real generator
  (Section 11) — Contract Design's job is naming and shaping the new
  interface, not revising settled ones, with the disclosed exception of a
  possible future `Confidence` field.
- **Placement:** genuinely open (Finding 3, Section 18) — Contract Design
  must decide whether `GoalPlanningHandoffCoordinator` itself is revised
  or a new coordinator is introduced, and should not treat this review's
  ownership recommendation as having silently answered that placement
  question.
- **What Contract Design must not attempt in the same pass:** resolving
  `WAITING_FOR_INPUT` reachability, the safety-refusal/incapacity
  distinction, cross-Goal conflict, or the Chapter 20/`PlanDecision` Open
  Question — each is a legitimately separable, larger question this
  review deliberately declines to fold into a single Contract Design, to
  avoid the same kind of retroactive-design problem
  `PLANNER_RUNTIME_CONTRACT_DESIGN.md`'s own "Why this unit exists"
  section already once had to correct for.

Contract Design may proceed, scoped to: the new Candidate Generator
interface's method signature and dependency shape; its exact input
contract (which of Section 5's legitimate inputs it actually receives,
and any resulting revision to `GoalPlanningHandoffCoordinator`'s own
signature or interception point); and where, structurally, it is
consumed. It must not expand into `WAITING_FOR_INPUT` implementation,
safety-refusal semantics, cross-Goal conflict handling, production wiring
of `PlannerRuntime`/`TaskManagerRuntime`, or Chapter 23's Goal Manager —
those remain separately chartered, per Section 16.
