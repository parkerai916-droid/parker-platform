## Answers to the fifteen questions

**1. What fact does `ExternalTranscriptionOwnerAuthorization.kt` persist?**
One durable record per evidence artifact: `{evidenceArtifactId, sourceSha256, principalId, purpose, approvedAt}` — the exact outcome of one prior, successful pass through the gate sequence in `ExternalTranscriptionOwnerAuthorizationCoordinator.authorize()` (below). It stores no credential, no session data, and no free-form owner input.

**2. Durable evidence of a decision made through the existing mechanism, or an independent determination?**
Both, and that is the correct, established shape — not a defect by itself. `authorize()` performs the real checks (Purpose active, manifest resolvable, high-authority verification, `PermissionEngine.evaluate`) exactly once, at creation; the durable record is then *consulted by lookup* (`isAuthorized`) on the hot path, rather than re-running the full ceremony on every read. This mirrors the codebase's own pre-existing pattern for durable authorization state (`OwnerUiAuthentication`'s session map after one real pairing ceremony; `FileSystemOrdinaryRegionAuthorizationStore`'s own grant record after `OrdinaryRegionIngestionWorkflow.authorize()`). The read path (`isAuthorized`) does not itself re-invoke `PermissionEngine` or `AuthorizationPurposeRegistry` — it is a pure existence check against a file that, in the current production wiring, can only ever be created by the one call site that performs those checks (verified: `store.createOrGet` has exactly one production caller — see Finding 1 below for the caveat).

**3. Does the permission policy remain authoritative?** Yes. `authorize()` calls the unmodified `permissions.evaluate(ExternalTranscriptionInvocationGate.buildExecutionRequest(...))` — the identical call the existing, unmodified `ExternalTranscriptionOwnerInvocationCoordinator.invoke()` already performs at execution time — and fails closed (`PERMISSION_POLICY_DENIED`) on anything short of `APPROVED`/`APPROVED_WITH_CONFIRMATION`. Confirmed by a passing test asserting denial even with a correct high-authority credential.

**4. Is Authorization Purpose still mandatory and exact?** Yes. The purpose is a fixed constant (`ExternalTranscriptionInvocationGate.AUTHORIZATION_PURPOSE`), never owner- or request-supplied; `purposes.isActive(purpose)` is checked and fails closed (`PURPOSE_NOT_ACTIVE`) first, before any other gate.

**5. Is authorization bound to the exact Evidence ID?** Yes, at every layer: the permission request's target/metadata, the grant record's `evidenceArtifactId` field, and the store's file key (a SHA-256 digest of the evidence ID) are all derived from the single `evidenceArtifactId` parameter passed into `authorize()`.

**6. Can authorization for evidence A ever authorize evidence B?** No, within this mechanism — confirmed by code trace and by a passing test. **However, see Finding 1**: at the *router* layer, the `ExternalEgressAuthorisation` signal `GovernedAcquisitionOwnerWorkflow` passes to `DeterministicEvidenceAcquisitionRouter.route(...)` is a single flat value applied to every capability in the registry for that evidence artifact — not scoped to which specific mechanism the owner actually consented to. This is a distinct, narrower issue from Q6 (it is not evidence-to-evidence leakage) and is not currently exploitable (see Finding 1).

**7. Can authorization for one purpose authorize another?** No. The grant's `purpose` field is always the fixed constant; `createOrGet`'s idempotency check requires an exact purpose match or fails closed (`Conflict`). `ExternalFileOwnerHighAuthorityVerification`'s generalization is itself purpose-scoped per instance (see Finding-adjacent note below) — it does not widen what any existing instance accepts.

**8. Can a paired UI session alone create authorization without high-authority verification?** No. Every `/owner/evidence/*` route (including the new authorize endpoints) requires `isAuthorised(exchange)` (the paired-device session) as a precondition just to be reached at all, but `authorize()` independently and additionally requires `ownerVerification.verify(...)` to pass — a missing or wrong credential fails closed (`HIGH_AUTHORITY_VERIFICATION_FAILED`) *before* the permission engine is even consulted. Confirmed by a passing test.

**9. Does the browser receive, persist, log, echo, or retain the secret?** No. The credential field is `<input type="password" autocomplete="off">`; it is read once into a local JS variable, POSTed as a raw request body (never a URL/query string), and never written to `localStorage`/`sessionStorage` or reflected back in any response. The server's JSON responses (`externalTranscriptionAuthorizationJson`) serialize only `{status, evidenceArtifactId, provider, purpose, disclosure, approvedAt, detail}` — no credential field exists on that type.

**10. Does the server persist or log the secret?** No. `OwnerVerificationCredential.toString()` is overridden to `"[REDACTED]"`. The durable grant record's `encode()` writes exactly five fields (evidence ID, source SHA-256, principal, purpose, timestamp) — the credential is not among them and cannot be reconstructed from the stored record. No log statement anywhere in the new code paths references the credential variable; the outer catch-all handler logs only the request URI (no query string is used) and the exception object, and no code path was found that could interpolate the raw credential into an exception message.

**11. Is the secret used only transiently for verification?** Yes. It exists only as a local variable through one call chain (`handleExternalTranscriptionAuthorization` → `authorizeExternalTranscription` → `authorizeExternalTranscriptionAsOwner` → `OwnerVerificationCredential.presented(...)` → `coordinator.authorize(...)` → `ownerVerification.verify(...)` → `constantTimeEquals`), then goes out of scope.

**12. Does creating authorization perform any provider call or evidence egress?** No — structurally, not just by test. `ExternalTranscriptionOwnerAuthorizationCoordinator`'s only dependencies are `EvidenceCustodian` (local), `AuthorizationPurposeRegistry`, `PermissionEngine`, `OwnerHighAuthorityVerification`, and the local file-backed store. None can reach a network; there is no reference anywhere in this class to `ExternalTranscriptionMechanism`, any HTTP transport, or any provider adapter.

**13. Is provider execution still separately governed after authorization exists?** Yes. `ExternalTranscriptionOwnerInvocationCoordinator.invoke()` — the class that actually calls the provider — is **byte-for-byte unmodified** by this unit and still performs its own independent `permissionEngine.evaluate(...)`, manifest/source verification, and representation-building before any provider call. The new authorization gate added in `ParkerRuntime.invokeExternalTranscriptionAsOwner` is strictly an *additional* precondition layered in front of that unchanged coordinator, not a replacement for anything it already checks. The existing, unmodified `ExternalTranscriptionOwnerInvocationCoordinatorTest` was re-run and passes 7/7.

**14. Does revocation/invalidation behavior remain fail-closed?** Vacuously, but see **Finding 2**: this new mechanism provides **no revocation capability at all** — once a grant file exists, there is no owner-facing or host-admin path to invalidate it (unlike the codebase's own established precedents: `OwnerUiAuthentication.revoke(deviceId)` and `FileSystemOrdinaryRegionAuthorizationStore.revoke(...)`). There is no "revoked but still honored" failure mode, because revocation was never built — that is a completeness gap, not an open-fail security hole, but it is inconsistent with established convention and should be added before this is treated as finished governance tooling.

**15. Was an always-off control converted into an application-controlled bypass rather than being satisfied through the intended architecture?** No. The value now fed into the router (`externalTranscriptionAuthorizationCoordinator?.isAuthorized(id) == true`) is sourced from a store that, in the current production wiring, can only be populated by successfully passing the full existing governed chain (Purpose-active → manifest-resolvable → high-authority-verified → permission-engine-approved). This is consuming the "egress/privacy authority" input fact the router's own governing scope lock always anticipated (§14), not an arbitrary flag flip.

## Findings requiring attention (neither is a parallel/bypass authorization system)

**Finding 1 — router egress signal is capability-indiscriminate (currently dormant).** `DeterministicEvidenceAcquisitionRouter.route(source, capabilities, egressAuthorisation: ExternalEgressAuthorisation)` takes one flat authorization value applied to *every* external-egress-requiring capability in the registry for that evidence artifact — this is a pre-existing property of the router's signature, not introduced by this unit. Today it is inert: the registry's plain "fidelity-first" external capability is separately, unconditionally hardcoded `AcquisitionAvailability.Unavailable(CONFIGURATION_NOT_ACCEPTED)` (a different, out-of-scope gap — see UI-INGESTION-4/5's own scope boundaries), and the "ordinary region" capability is absent from the registry entirely because `PARKER_ORDINARY_REGION_INGESTION_ENABLED` is not configured in this deployment. **If ordinary-region ingestion is ever enabled in a deployment that also has this new authorization feature configured, an owner's "Authorize enhanced transcription" confirmation for one document would also satisfy the router's egress gate for the unrelated ordinary-region/crop mechanism for that same document**, without the owner ever having seen that mechanism's own disclosure text. Recommendation: give the router (or the workflow layer) a capability-scoped egress-authorization signal before both features are ever enabled together.

**Finding 2 — no revocation path.** See Q14. Recommendation: add an owner- or host-admin-facing revoke operation before this is presented as complete authorization tooling, mirroring `FileSystemOrdinaryRegionAuthorizationStore.revoke`.

**Finding 3 (minor, robustness only) — a corrupted grant file throws rather than fails closed gracefully.** `FileSystemExternalTranscriptionAuthorizationStore.loadIfPresent` calls `decode`, whose integrity check (`require(parts.last() == digest(body))`) throws `IllegalArgumentException` on a tampered/corrupted file rather than returning `null`. This still cannot grant unauthorized access (no code path here fails *open*), but it does mean `isAuthorized`/`status` would propagate an uncaught exception instead of a clean denial. Cosmetic/robustness only.

**Finding 4 (observation, not a defect) — two independent durable ledgers now exist for the identical Authorization Purpose value.** `OrdinaryRequestRegionV8Execution.kt` already defines `REQUEST_REGION_V8_AUTHORIZATION_PURPOSE = ExternalTranscriptionInvocationGate.AUTHORIZATION_PURPOSE.value` and gates the pre-existing, separate `FileSystemOrdinaryRegionAuthorizationStore` with it. This unit's new store is a second, independent ledger for the same purpose string, serving a different mechanism. This is **not a pattern introduced by this unit** — it follows a precedent this codebase's own prior authors already established for the closely related ordinary-region capability. Direct reuse of `FileSystemOrdinaryRegionAuthorizationStore`/`OrdinaryRegionOwnerAuthorization` was considered and rejected during implementation because that record's shape (a `capabilityDigest` requiring `OrdinaryRegionCapabilityIdentity.digest()`, and a disclosure string hardcoded to describe "authoritative PDF evidence crops") is structurally coupled to the region/crop mechanism and would have misrepresented to the owner what a whole-document "enhanced transcription" authorization actually covers. Worth a future consolidation unit, not a blocking defect — and Finding 1 is the concrete consequence of this bifurcation that actually matters.

**Note (not a defect) — the high-authority credential is not itself cryptographically bound to the target.** `ExternalFileOwnerHighAuthorityVerification.verify()` checks only `target.value.isNotBlank()`, not any target-derived value — the same physical shared secret verifies for any target equally. This is unchanged, pre-existing behavior inherited unmodified from the human-correction mechanism (`HumanCorrectionPermissionPolicy` has the identical property today). Exact-target binding is instead enforced structurally: the server, not the browser, determines which evidence artifact `authorize()` acts on, and the durable record is keyed to exactly that identity.

## Generalization safety re-check

`ExternalFileOwnerHighAuthorityVerification.load(path, allowedPurposes = setOf(HUMAN_TRANSCRIPTION_CORRECTION_PURPOSE))` — the default preserves every pre-existing call site's behavior exactly. Two independent instances are constructed in production (`ParkerRuntime.kt:1250` for human correction, unchanged default; `ParkerRuntime.kt:1653` for enhanced transcription, explicit `allowedPurposes = setOf(ExternalTranscriptionInvocationGate.AUTHORIZATION_PURPOSE)`) — both load the same underlying secret file, but each instance accepts only its own configured purpose set. Neither instance can be tricked into accepting the other's purpose. `HumanCorrectionPermissionPolicyTest` (existing, unmodified) was re-run and passes 5/5, confirming the human-correction path is unaffected.

## Verdict

**A — AUTHORIZATION ARCHITECTURE PRESERVED — CANDIDATE ELIGIBLE FOR OWNER ACCEPTANCE**

The core authorization architecture — Authorization Purpose (exact, mandatory), permission-policy evaluation (authoritative, unmodified), owner high-authority verification (reused additively, non-weakening, purpose-scoped per instance), exact evidence-ID binding, fail-closed behavior on every mismatch tested, and complete separation between authorization creation and provider execution — is genuinely reused, not duplicated, and not bypassable through any path found in this review. The "always-off" state this unit replaced was a placeholder the router's own governing scope lock anticipated being filled, not a constitutional prohibition.

This is not an unconditional pass: **Findings 1 and 2 are real, and Finding 1 in particular must be resolved (a capability-scoped egress signal) before `PARKER_ORDINARY_REGION_INGESTION_ENABLED` is ever turned on in any deployment alongside this feature.** Neither finding is currently exploitable in this deployment's actual configuration, and neither constitutes a parallel or bypass authorization mechanism for the specific capability this unit wires up.
